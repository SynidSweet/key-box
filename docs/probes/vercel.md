# Probe report: Vercel (KBOX-42)

Probed 2026-11-12 from an agent workstation with no credential (S-705: no admin or master key exists off the key box). No throwaway
project was used; items that need an authenticated request are listed under "Left for the box".

All requests went to `https://api.vercel.com` with `Authorization: Bearer kbox-probe-invalid`. Method used: a real route answers
`403 {error:{code:"forbidden",message:"Not authorized",invalidToken:true}}` (or `400` naming a missing body field); an unknown route answers
`404 {error:{code:"not_found",...}}`. Each path was compared with a made-up sibling.

## Spec corrections

- `POST /v1/teams/t/invites` is not a Vercel route (404; `GET` on the same path is a real route, 403). Inviting a user is `POST /v2/teams/{teamId}/members` (403). The `mustDeny` sample and its path pattern must change (see `vercel.mustdeny-team-invites`).
- `POST /v1/projects/p/protection-bypass` is not a route (404); the route is `PATCH /v1/projects/{idOrName}/protection-bypass` (403). The sample must use `PATCH` (see `vercel.mustdeny-protection-bypass`).

## Facts for the adapter

- Error shape for every failure: `{"error":{"code","message"}}`; a bad or fake token adds `"invalidToken": true` with status 403 (not 401). The verifier can map 403 with `invalidToken` to `rejected`. Observed on all routes above.
- Validation can run before authentication: a body missing a required field answers 400 naming the field even with a fake token (`name` for `/v11/projects`, `/v10/projects/{p}/domains`, `/v13/deployments`, `/v3/user/tokens`; `projectId` for the domain `move`). Observed.
- Token creation: `POST /v3/user/tokens` body schema `name` (required), `expiresAt` (number), `projectId`; no other property allowed (`additionalProperties: false`); response `{bearerToken, token}`. Doc: https://openapi.vercel.sh/ (`createAuthToken`).
- Token read: `GET /v5/user/tokens/{tokenId}` accepts the literal `current` for the calling token; it is under `/user/tokens`, so `mustDeny` blocks it for relay (fine, the verifier runs in core). Doc: `getAuthToken`.
- Token list: `GET /v6/user/tokens` returns `{tokens[], pagination:{count,next,prev}}`. Doc: `listAuthTokens`.
- Env create: `POST /v10/projects/{idOrName}/env`, query `upsert=true`, `teamId` or `slug`; body one object or an array of `{key, value, type, target[], gitBranch?, comment?, customEnvironmentIds?}`, `type` enum `system|encrypted|plain|sensitive`, `target` items `production|preview|development`; `target` or `customEnvironmentIds` required. Doc: `createProjectEnv`.
- Env edit: `PATCH /v9/projects/{idOrName}/env/{id}` body (no extra properties) `key, target, gitBranch, type, value, customEnvironmentIds, comment`. Env delete: `DELETE /v9/projects/{idOrName}/env/{id}` (query `customEnvironmentId`, `teamId`, `slug`); batch delete `DELETE /v1/projects/{idOrName}/env`. Env list/read: `GET /v10/projects/{idOrName}/env`, `GET /v1/projects/{idOrName}/env/{id}`. The env id comes from the list, so an update or delete needs a prior `GET` (sensitive values are not returned). Doc.
- Redeploy: `POST /v13/deployments` query `forceNew`, `skipAutoDetectionConfirmation`, `teamId`, `slug`; body properties include `deploymentId`, `name` (required by the schema), `project`, `target`, `withLatestCommit`, `meta`. The doc says all settings and env vars are inherited. The CLI's `redeploy` sends `POST /v13/deployments?forceNew=1` (`commands/redeploy/index.ts:161`). Redeploy therefore needs the token to be allowed to create deployments on the project.
- Create project: `POST /v11/projects` query `teamId` or `slug`; `name` required, max length 100, lower-case letters, digits, `.`, `_`, `-` per the doc (not observed; verify the pattern with the throwaway project). Other body fields (doc): `framework, gitRepository, buildCommand, installCommand, outputDirectory, rootDirectory, environmentVariables, ...`. For `createProject` send only `name`.
- Domains: add `POST /v10/projects/{idOrName}/domains` body `{name, gitBranch?, customEnvironmentId?, redirect?, redirectStatusCode?}` (400 if the domain is already on that project; response carries `verified` and a `verification` challenge); remove `DELETE /v9/projects/{idOrName}/domains/{domain}` optional body `{removeRedirects}`; move `POST /v1/projects/{idOrName}/domains/{domain}/move` body `{projectId (target), gitBranch?, redirect?, redirectStatusCode?}`; update `PATCH /v9/projects/{idOrName}/domains/{domain}`; verify `POST /v9/projects/{idOrName}/domains/{domain}/verify`. All take `teamId` or `slug`. Adding a domain that another project holds is likely refused (doc silent): move is the way to take it over. Doc: `addProjectDomain`, `removeProjectDomain`, `moveProjectDomain`.
- Team settings: `PATCH /v2/teams/{teamId}` (`patchTeam`). Body properties in the doc: `name, slug, description, avatar, emailDomain, previewDeploymentSuffix, regenerateInviteCode, saml, enablePreviewFeedback, enableProductionFeedback, sensitiveEnvironmentVariablePolicy, disjunctiveProductionSecretPolicy, remoteCaching, hideIpAddresses, hideIpAddressesInLogDrains, dpAccessRequestsMode, requireVerifiedCommits, disableRepositoryDispatchEvents, defaultDeploymentProtection, defaultPassport, defaultExpirationSettings, deploymentPolicy, strictDeploymentProtectionSettings, strictShareableLinks, strictPasswordProtectionSettings, strictConnectors, nsnbConfig, defaultProjectJobs, resourceConfig`. For KBOX-26's fixed list exclude `regenerateInviteCode` (invites), `saml` and `emailDomain` (sign-in and membership), `slug` and `name` (identity, owner decision), `strict*` owner-only policies and `resourceConfig`/`nsnbConfig` (billing-like); a candidate safe list is `previewDeploymentSuffix, enablePreviewFeedback, enableProductionFeedback, sensitiveEnvironmentVariablePolicy, remoteCaching, hideIpAddresses, hideIpAddressesInLogDrains, requireVerifiedCommits, disableRepositoryDispatchEvents, description`. Members, invites, tokens, integrations and billing have no field in the body except `regenerateInviteCode` and `saml`. The final list is a spec decision.
- Mixed API versions per route: members are `GET /v3/teams/{teamId}/members` (and an undocumented `GET /v1/teams/{id}/members`, 403 observed), invite is `POST /v2/teams/{teamId}/members`, invites list `GET /v1/teams/{id}/invites` is a real route (403 observed, not in the OpenAPI file). The `mustDeny` rule should match by path shape across versions, for example `/v{n}/teams/{id}/members{rest:**}` and `/v{n}/teams/{id}/invites{rest:**}`.
- Sample fixes for the deny list: integrations sample needs `?view=account` to pass validation; protection bypass is `PATCH /v1/projects/p/protection-bypass` (also `PATCH /aliases/{id}/protection-bypass`, undocumented version prefix); `GET /v1/drains` accepts `projectId, includeMetadata, includeDeliveryStats`.
- CLI and a project token: `vercel deploy` and `vercel pull`/`env pull` have code paths for a project-scoped token (`allowOwnerLookupFallback`, `skipOwnerLookup`), with `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` set; other commands call `GET /v2/user` first and fail on 403. Source above. Delivering a project token for `deploy` and `env pull` use is supported by the CLI source; the claim stays unobserved.

- `vercel.env-upsert`: `POST /v10/projects/{p}/env?upsert=true` with a key that already exists, `type: "sensitive"`, `target: ["production"]`; expect 200 and the same key id, no duplicate.
- `vercel.env-update`: `GET /v10/projects/{p}/env` for the id, then `PATCH /v9/projects/{p}/env/{id}` with `{value}`; check whether `type: sensitive` can be edited and whether `target` must be resent.
- `vercel.env-delete`: `DELETE /v9/projects/{p}/env/{id}` on a sensitive variable; expect 200.
- `vercel.env-list-pagination`: on a throwaway project with more variables than one page could hold, `GET /v10/projects/{p}/env`; record whether the answer carries a `pagination` object or a limit, and how the next page is asked for.
- `vercel.redeploy`: `POST /v13/deployments` with `{deploymentId, name}` only, then with `{deploymentId, name, target:"production"}`; record whether `name` is needed and whether new env values are picked up.
- `vercel.verifier-project-token`: with the project token, `GET /v2/user`, `GET /v5/user/tokens/current`, `GET /v9/projects/{id}`; record statuses and pick the cheapest call that returns 200 for a project token and 403 `invalidToken` for a revoked one.
- `vercel.vcp-core-length`: create two tokens with the master token and measure the character count after `vcp_` (names and counts only, never values), including an `expiresAt` token and a `projectId` token.
- `vercel.create-project`: `POST /v11/projects` with `{name}` on the master token, then delete it; also send an uppercase and an overlong name to see the pattern error.
- `vercel.set-domain`: add, move and remove a throwaway domain between two throwaway projects; record the answer when the domain is on another project and when it is unverified.
- `vercel.create-project-answer`: `POST /v11/projects` with `{name}` twice; record whether the answer carries `id` (the box reads it), the status and `error.code` of the second (a duplicate name), and that an uppercase and an overlong name are refused (the box's name shape is `^[a-z0-9][a-z0-9._-]{0,99}$`).
- `vercel.set-domain-repeat`: add the same domain twice, remove one that is absent, and move one to the project that already has it; record each status and `error.code` (names only).
- `vercel.domain-move-target`: `POST /v1/projects/{p}/domains/{d}/move` with `projectId` as the target project's name, then as its `prj_` id; record which is accepted.
- `vercel.team-settings`: `PATCH /v2/teams/{id}` with each candidate setting alone, with the classic team-scoped master token, on a throwaway team; record which are accepted, and confirm `strict*` and billing-like fields.
