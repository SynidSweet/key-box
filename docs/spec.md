## In plain words

The key box is a small computer of its own, rented free from Oracle, that holds the keys which could do real damage: the admin keys and the keys that make
other keys. Nobody logs into it, and the agents have no way in. Your phone is the only thing that can tell it to do something that matters, with your
face or fingerprint, in an app you put on your home screen.

An agent that needs an admin key does not get the key. Its program sends the request to the key box instead of to the platform (OpenAI, Supabase,
Google). The box checks that the computer asking holds a pass you approved and that the key was granted to it, passes on only the kinds of request named
in advance, adds the key itself, and sends the answer back. If the answer carries anything shaped like a key, the box holds it back. A request that
would make a new key, a new login or a new password is never passed on.

The box also changes keys on a schedule. It makes a new key, puts it where the old one was, restarts the apps that need it, checks that all works, and
only a day later switches the old key off. If anything fails, the old key stays and you get one message. Ordinary keys change without asking you. Admin
keys wait for your phone, one at a time. Where a platform cannot make keys on request (Anthropic, Stripe), you copy the key on your phone and paste it in
the app.

The box can also update itself, but only to the exact version your phone approved. The approval page says that agents wrote and checked that version and
that nobody you trust has read it. That is true and the box cannot make it better; it only makes sure that what runs is what you approved.

The box writes a file of one-way fingerprints of the admin keys, which your computer uses to notice a stray copy of one. It never shows a key, a length or
the start or end of a key anywhere, except in two named cases (an ordinary key it made for your computer, and the public opening letters of a key's
format in the fingerprint file).

What it does not do: it cannot stop an update you approve from taking every key; it cannot stop an app that agents wrote from reading the keys that
app is given; it cannot tell which agent on a machine holding a pass is calling. A pass that leaks works from anywhere until you switch it off in one tap,
and the box's log records every use. If you lose your phone, you get back in only through the authenticator app synced to your Google account (design §8).

## Contradictions found in the design (read before building)

1. Design §0, §1.5 step 1, `KBOX-20` (first paragraph), §7 and R7 still say the authenticator app has cloud sync and backup off and that a lost phone
   cannot be recovered. Revision 5 (§8, `KBOX-20` third bullet, §11 Q3) says the app syncs to a Google account never signed in on the owner's machines, so a
   lost phone IS recoverable. **This spec follows §8/§11** (the later, owner-answered text). The setup checklist and the recovery text (`KBOX-48`) carry the
   new wording. S-711 as filed still says "does not sync" until card C-692 lands.
2. Design §1.3 says the lend socket checks `SO_PEERCRED`. Node's standard library has no peer-credential API, and zero npm dependencies is a settled rule.
   This spec makes the operating system check it instead: socket mode and directory ownership (`KBOX-3`, `KBOX-45`).
3. Design §10 unit 6 (share file) tests against devbox's `admin-match` finding every planted copy, but the v3 backend in `admin-match` is unit 9, built
   after unit 6. `KBOX-33` closes this with a reference matcher written in the box's test kit and a golden corpus that devbox unit 9 runs too.
4. Design §10 unit 2's test "enrol without an open window and without a control token refused" can be read two ways. This spec reads it as: a
   `scope: control` enrol needs the open window; a `scope: relay` enrol needs no token and only creates a proposal (`KBOX-53`).
5. Design header says "revision 4" while sections 8 and 11 carry revision 5 text. No behaviour depends on it.

### Unit `scaffold`: the repo, the toolchain and the shared test kit

**`KBOX-27` One toolchain, no runtime packages.** The choices in the toolchain table hold. Source: design §1.3 (zero npm runtime dependencies, run from source by
type stripping). Test (`test/arch.test.ts`): `package.json` has no `dependencies` (and the keys of `devDependencies` are exactly `typescript` and `@types/node`, each an exact version with no range, `@types/node`'s major equal to `.nvmrc`'s; `tsconfig.json` has `types` equal to `["node"]`; no `.d.ts` file in the repo declares a `node:*` module; `package-lock.json` exists; no file of the release tree is under `node_modules`; no `src/` file imports either dev package); every import specifier in
`src/` is a `node:` builtin or a relative path ending `.ts` or `.js`; no file under `src/` uses TypeScript-only runtime syntax (enum, namespace, parameter
property: checked by running every `.ts` file through `node:module` `stripTypeScriptTypes` and comparing the line count and a re-parse); `tsc --noEmit` is
clean with the strict options of the table; the counts of `any`, non-null `!`, `@ts-ignore`, `@ts-expect-error`, `eslint-disable` and `noqa` are zero.

**`KBOX-28` Pure core, imperative shell, no cycles, no silent catch.** Source: design §1.3 (trusted core), code-doctrine. `src/pure/**` imports no
`node:fs`, `node:net`, `node:http*`, `node:tls`, `node:dns`, `node:os`, `node:child_process`, `node:sqlite`, `node:worker_threads`, and uses none of `Date.now`,
`new Date()` without an argument, `Math.random`, `setTimeout`, `setInterval`, `fetch`, `process.`, `randomBytes`, `randomUUID`, `randomInt`, `generateKey*`
(hashing, HMAC, HKDF, signature verification and AES-GCM with a given IV are allowed). Randomness, time, files, sockets and the database come in through
the ports of `src/ports/`. `src/ports` and `src/pure` import nothing from `src/shell` or `src/platforms`. There is no import cycle (type-only and dynamic
imports included). Every `catch` rethrows, reports through the `Audit` or `Notifier` port, or returns an error result; an empty catch or a catch that only
logs is refused. Test (`test/arch.test.ts`, using `typescript` as a parser): each of these on a fixture that breaks it fails, and the repo's own tree passes.

**`KBOX-35` The shared test kit and the contract suites.** Source: design §10 ("every unit starts by writing the failing tests"), test-doctrine R3, R7, R9,
section 5. `test/kit/` provides, and tests use instead of hand-built setup: `tempDir()` (removed in an `after` hook), `FakeClock` (time is always passed in),
`seededRandom(seed)` (the seed is printed on failure; property tests take it from `KB_SEED` or draw one and report it), `canary()` (fresh random bytes and
`assertAbsent(surfaces)`, which looks for the bytes raw, base64 std and url, hex, percent, JSON-escaped and `\u`-escaped in each named surface: database file

its real ways: refuse, hang, 500, 401 with an echoed key hint, malformed JSON, partial body, redirect), `drive()` (talks to a started core or relay over its
unix socket). One contract suite per port in `test/contracts/` (`issuer`, `lister`, `verifier`, `destination`, `redeployer`, `relayProfile`, `vault`,
`approvals`, `audit`) is written once and run against the fake and, in each adapter unit, against that adapter over `fakePlatform()`. Other tests never mock
or spy on this repo's own modules or database; faults are injected through a port or through `fakePlatform()`. The canary suite
(`test/canary.test.ts`) is extended by every unit that adds a response, log line or event. Test: the kit's own behaviour is tested only where it is
tricky (`assertAbsent` finds a planted base64 copy and a `\u` copy and returns clean on a decoy; a failing `fakePlatform()` mode really fails).

**`KBOX-42` An adapter starts with a live probe, reported before code.** Source: design §5.4, §12. Each platform folder `src/platforms/<id>/` needs
`docs/probes/<id>.md` committed first. It lists every UNVERIFIED item this spec names for that platform with one line each: the request sent to a

### Unit `forms`: the leak-scan forms library

**`KBOX-54` One forms library for both scanners.** Source: design §1.1 (response scanner, fingerprint writer), `KBOX-14`, §6.5, devbox
`admin-secrets-spec.md` §3 and §4 (normative for the forms; this is a port to TypeScript). `src/pure/forms.ts` is the one place that computes, for a stored
value: its **core** (a JWT: the signature; a value with a known prefix: the rest; a URL with userinfo: the password as written; else the whole value) and its
**forms**: raw; base64 standard and url interiors at byte alignments 0, 1, 2 (the interior is the characters fixed by the core's bytes alone); hex lower and
upper; percent (one form: `encodeURIComponent` style, Python `quote` style and the `safe=''` style, with upper- and lower-case escape digits); JSON-escaped
(also `/` as `\/`) where it differs from raw; `\uXXXX` with every character escaped, lower and upper hex. Two sets are exported: `scanForms` (all of them, for
the relay's response scanner) and `shareForms` (raw plus the six base64 interiors, for the share file). It also exports the stripped view (a run of whitespace or the `\`-newline pattern of at most 4 bytes, the longest line-break pattern being `\` CR LF, is removed; a longer run is kept as one separator byte, so no copy spans it and a whitespace flood is never held; with a map from a stripped offset back to the raw one) and a streaming matcher that finds a form across chunk boundaries and reports how many raw bytes it can already release. **The hold-back is counted in the stripped view:** it holds back the last (longest form minus 1) stripped characters and every raw byte from the raw offset of the first of them on, the removed bytes between and after them included, so no byte of a match, wrapped or not, is released before the match completes. The library never logs, throws with, or returns any part of a value in an error; a failure is a fixed code.
Test (`test/forms.test.ts`): known-answer tables for each form on short synthetic values; properties with a seeded generator (R6): for any core, prefix and
suffix, every form of the core is found inside the same encoding of prefix, core and suffix at some alignment, and a copy split across any chunk boundary is
found exactly once and the release point never passes the start of a planted copy, at every split, including a wrapped copy (base64 at 64 and 76 columns with CRLF, `\`-newline: the release point is in raw bytes and the hold is counted in stripped characters, so a raw-byte hold of the same size fails this property); a whitespace run longer than 4 bytes is not removed and a copy split by it is not found; the held raw bytes of a 10 MiB run of line breaks are constant; a wrapped copy (base64 at 64 and 76 columns, CRLF, `\`-newline) is found only in the stripped view and maps back to the right offset; a
decoy (a value differing in one core byte) is never found; the failure paths (empty value, a core shorter than the form's minimum window) return fixed codes.
The independent oracle for the tables is reported by the builder (`worker-routine`): the cheapest honest source is devbox's own `admin-match` form
functions run on synthetic canary values through its test seam; if that is not usable the builder says so and uses hand-computed vectors for values of 1, 2
and 3 bytes plus the substring property.

### Unit `kernel-store`: the vault, the database, the audit log, the machine API frame and the events

**`KBOX-2` A value leaves the box only to an approved destination or a relayed upstream.** Source: design §1.2. No page, machine-API response, log line,
audit entry, event, error, metadata export or Web Push payload carries a value, a length, a prefix, a suffix or an unkeyed digest. Two exceptions: a
box-issued **ordinary** key is delivered to the workstation destination (`KBOX-34`), and the signed share file carries, for anchored entries only, the public
prefix of the key's format (from the adapter's `shape`, never read from the value) and `len`, the length of the digested run (`KBOX-33`). Windowed entries carry no length: no `len`, a constant stride and a constant probe count whatever the key's length (`KBOX-33`). A coverage tier
name is not a length. **Two more things the public share file shows, named here so the exception list is complete:** its salted HMAC digests and probes (anyone who reads the file can test guesses against them; they are safe only because each digested window or anchored run holds at least 72 random bits, `KBOX-18`, so S-128 holds for the specified shapes and for no other; the 72 bits are counted over the digested run itself in each form and alignment, not over the whole core; an anchored key's standard and URL-safe base64 digests are equal exactly when its run holds none of `+ / - _`, which tells a reader about one bit and is accepted), and the **tier** itself, which tells a reader a length class (a windowed entry means a core of 32 to 256 characters, an anchored one a core of at least 72 bits behind a known prefix). Neither is a value, a length or a prefix beyond the stated exceptions; both are accepted and are not to be widened. Test: the canary suite (`KBOX-35`) after add, rotate, relay, a failed rotation and a paste; the canary is absent from every surface
listed in `KBOX-35`, except the declared prefix and anchored `len` in the share file and the delivery route (the share file's own length-blindness test is in `KBOX-33`). A seeded property test feeds random byte strings through the audit
and event writers and the error mapper and finds none in the output.

**`KBOX-4` Values are lent, never returned.** Source: design §1.2. The vault port is `put(ref, gen, bytes)`, `lend(ref, gen)` and `retire(ref, gen)`; `lend`
returns a `Lent` whose `use(fn)` hands the bytes to `fn` and whose `toString`, `toJSON` and `util.inspect` all return `[key <ref>:<gen>]`. Every adapter call
is wrapped: anything it throws is replaced by a fixed text plus the platform's HTTP status (the same pattern as mission control's KREQ-12), and a create
response that holds a new value is never logged, even when it fails to parse. **`KBOX-5` The metadata database never holds a value, by construction.** Source: design §1.2. Values live only under the vault directory. The metadata
database (`meta.db`: keys, classes, grants, destinations, schedules, rotation state, approvals, coverage, machine token hashes) is exported in full through

**`KBOX-56` Schema versions.** `meta.db` and `private.db` each carry a schema version in `PRAGMA user_version`; the schema of release 1 is version 0, and every table it creates is still created by its release-1 `CREATE TABLE IF NOT EXISTS` text, never edited. Opening a file runs all of that file's version-0 statements in one place (`openMetaDatabase`: the kernel's, the rotation store's and the paste tasks', so those tables exist whether or not rotation is opened; `openPrivateDatabase`: its own), and then, before any other read, the pending migrations from an ordered list per file (`src/shell/migrations.ts`; entry `i` brings the file from version `i` to `i+1`). Each migration runs in one `BEGIN IMMEDIATE` transaction that re-reads `user_version`, applies the migration and writes `user_version`, so a second process opening the file at once waits and finds it done, and a migration that fails leaves the file at its old version and core does not start (`schema_migration_failed`, audited by code only). **Migrations are additive only**: a new table, a new nullable column or a new index; never a dropped or renamed column, a changed `CHECK`, a new `NOT NULL` without a default, or a rewritten row. Reason: a failed update runs the previous release over the same files (`KBOX-6`), so the release before must keep working on a newer file; a file whose version is higher than the code knows is therefore opened as is, and only `schema_newer` is logged once at start. A release that needs a non-additive change needs a new rule first. Migration 1 of `meta.db` adds `rotation_keys.verify_hint TEXT` (`KBOX-40`). Test (`test/migrations.test.ts`, temp dirs): a `meta.db` and `private.db` written by the version-0 schema (the release-1 statements extracted from tag v1, kept as a fixture file of SQL text) migrate to the newest version with every row kept; a version-0 `meta.db` holding only the kernel tables (a release-1 box without a domain) reaches the newest version with the rotation and paste tables present; a new empty file reaches the newest version; `openCore` alone on a new directory has `rotation_keys.verify_hint`; core started without `KB_DOMAIN` on a version-0 file starts and serves `GET /api/meta`; opening twice runs each migration once; a migration that throws leaves `user_version` and the tables unchanged and core does not start; a file at a version above the newest opens and serves `GET /api/meta`; the code's version-0 statements equal the fixture's (whitespace aside), so a column added by editing a `CREATE` fails; an arch check refuses a migration statement containing `DROP`, `RENAME`, or `ALTER TABLE … ALTER`, and a `NOT NULL` column added without a `DEFAULT`.

**`KBOX-10` Machine API token rules.** Source: design §2. Bearer tokens are 32 random bytes, base64url (43 characters), with the prefix `kbt_`. The box

machine API. Phone routes accept no bearer token; the machine API accepts no passkey assertion. A token is compared by its hash in constant time. Test:

prefix) gets 401 with no database lookup (counted through the port); two tokens whose hashes share a long prefix are told apart.

**`KBOX-19` Backups: none of values; metadata goes to mission control.** Source: design §8. There is no backup of vault files and no code path that writes
one (a test greps the shell adapters for any copy of a vault path). The metadata database is exported on change as events plus `GET /api/meta` (`KBOX-30`).
Test: after a change to a key row, a destination row and a grant row made through the metadata port, the next event after the change has kind `key.changed` and `GET /api/meta` shows it (route-level versions of this check sit in the unit that owns each route: `rotate` for key issue, rotation and retirement, `kernel-approve` for the executed grant and destination approvals); the export

**`KBOX-29` Wire conventions of every machine-API route.** Source: design §2, §6.3; decided here. HTTPS only (Caddy), JSON bodies UTF-8 with
`Content-Type: application/json`, except the octet-stream routes named in `KBOX-34`. Times are integers in milliseconds since the epoch, named `*_at`.
Every `/api/*` request needs `Authorization: Bearer kbt_…` of a token with the route's scope (`KBOX-11`, `KBOX-30`). Every response carries
`Cache-Control: no-store` and `KB-Api-Version: 1`. Errors have one shape, `{"error":{"code":"<snake_case>","message":"<fixed text>"}}`, and never echo
request text. Codes: `bad_request` 400, `browser_call` 403, `unauthorized` 401, `forbidden` 403, `not_found` 404, `slot_taken` 409, `conflict` 409,
`too_large` 413, `unsupported_media` 415, `rejected` 422 (a value that failed its checks; the reason is a names-only code), `unavailable` 503 (a dependency
inside the box is down), `internal` 500 (fixed text; the cause goes to the audit log as a code). JSON request bodies are read up to 64 KiB (a mechanical
safety bound for parsing, not a policy limit; decided here and easily raised); a body over it gets `too_large`. A body is parsed once into a typed value at
the edge (closed object, unknown member refused, string lengths and shapes checked); the interior takes only parsed types. Request ids: `req_` plus 12
random base64url characters, echoed as `KB-Request-Id` and written to the audit log. Test (`test/api-frame.test.ts`): each code is produced by a request that
should get it and its body matches the fixed text; an unknown member, a wrong type, a body of 64 KiB + 1 and a body with a BOM or invalid UTF-8 are refused
with no state change; an error body never contains a canary placed in the request.

**`KBOX-30` Control read routes: metadata and audit.** Source: design §6.2, §6.3; shapes decided here. Scope `control` only.
- `GET /api/meta` returns `{cursor, box, keys, machines, approvals}`. `cursor` is the event sequence number at the moment of the snapshot (a new client starts
  its long-poll there). `box` is `{release, share_version, share_public_key_ed25519_b64, oidc_issuer, epoch}`; `epoch` is 8 random hex characters chosen when `meta.db` is created, so a rebuilt box has a different one. A key is `{keyref, platform, name, projects,
  class, status, gen_current, destinations:[{kind, target, readable_by}], schedule:{rotate_every_days, grace_hours, next_due_at, expires_at}, grants:[{machine}],
  allow_rules:[ruleId], coverage, last_use_at}` where `class` is `ordinary|admin|master`, `status` is `works|rotating|awaiting_approval|awaiting_paste|failed`
  and `coverage` is `windowed|anchored|none|null` (null until measured). A machine is `{label, scope, enrolled_at, revoked, last_network}`. An approval is
  `{approval_id, kind, title, slot, opened_at, expires_at}` where `title` is the box's one-line title (`KBOX-8`). Nothing in `private.db` and no token
  hash appears.
- `GET /api/audit?since=<seq>&limit=<n>` returns `{entries, cursor, more}`: each entry is the audit row of `KBOX-50` with `seq`, `at`, `prev_hash`, `hash`.
  `limit` is optional; without it all rows after `since` come back.
Test (`test/control-read.test.ts`): the exact member set of each response is pinned by a closed-schema parse in the test (a new member fails it); a revoked
or relay-scope token is refused; a snapshot taken during a write is consistent with its `cursor` (replaying events after `cursor` on the snapshot gives the
final state); the canary is absent.

**`KBOX-31` Events and the long poll.** Source: design §1.1 (Notifier), §2, §6.3; shapes decided here. Events are append-only rows `{seq, at, kind, data}` in
`meta.db`, `seq` a strictly increasing integer from 1. `GET /api/events?since=<seq>&epoch=<epoch>` (scope `control`; `epoch` optional) answers at once with the events after `since` if there are
any; otherwise it holds the request for 25 seconds and then answers `{events:[], cursor:<since>}`; a response with events is `{events:[…], cursor:<last seq>}`.
A missing `since` means the current head (no replay). `since` greater than the head is `bad_request` when `epoch` matches or is missing. An `epoch` that differs from the box's is 409 `conflict` with `detail.code: "epoch_changed"`: a rebuilt box restarts `seq` at 1, and the client must take a new snapshot from `GET /api/meta` and poll again from its cursor and epoch. Events are never deleted in v1 (they hold names only).
The closed list of kinds and their `data` (names, ids and codes only, never a value):

| `key.changed` | `keyref` |
| `rotation.state` | `run_id, keyref, state, step` |
| `rotation.failed` | `run_id, keyref, step, reason_code, old_key_works` (boolean, the fact at notice time: `false` for a failed create run, which has no old key, and for an `overlap: false` key whose `set(old)` could not be done yet; `true` otherwise) |

| `delivery.ready` | `delivery_id, keyref, project, name, gen` |

| `update.state` | `approval_id, state: pending\|installed\|rolled_back` |

Test (`test/events.test.ts`, `FakeClock`): the long poll returns on the first event, returns an empty batch at 25 s of fake time, and two concurrent pollers

**`KBOX-43` The client address comes from one header.** Source: design §1.3 (client address). Both processes read the client address only from
`X-KB-Client-Ip`, only from a connection on their unix socket, and ignore `X-Forwarded-For`, `X-Real-IP` and `Forwarded`. A missing or malformed header

**`KBOX-45` Process layout, sockets and unit hardening.** Source: design §1.3. Three system users (`caddy`, `keybox`, `keyrelay`), three long-running units and the root installer `kb-install` (`KBOX-6`). **Three runtime directories**, created at boot by `deploy/keybox-tmpfiles.conf` (systemd-tmpfiles, which runs as root, so no service needs privilege to make them), each mode 2750 (setgid, so a socket created inside takes the directory's group and no `chown` call is needed; the units set `UMask=0007`, so sockets are 0660): `/run/keybox` owner `keybox` group `caddy`, holding core's `http.sock`; `/run/keyrelay` owner `keyrelay` group `caddy`, holding the relay's `http.sock`; `/run/keybox-lend` owner `keybox` group `keyrelay`, holding `lend.sock`. One directory can serve only one group, which is why the lend socket has its own. The result: Caddy reaches both `http.sock` files and not the lend socket; the relay user reaches the lend socket and not core's `http.sock` (it cannot even list `/run/keybox`), so it cannot forge `X-KB-Client-Ip` to core; no one is put in another's group and the only `SupplementaryGroups` of any unit is the root `kb-code` unit's `tty` (`KBOX-20`). (The operating system, not a peer-credential call, is the access check: Node has none.) The same file makes two root-owned directories for the installer (`KBOX-6`): `/etc/keybox` (0755, holds `trust.json`) and `/var/lib/keybox-install` (0755, holds the install results); `keybox` can read both and write neither. Each unit has `LimitCORE=0`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `PrivateTmp=yes` and `ReadWritePaths=` naming only its own directories; kb-relay has no read access to the vault directory (`InaccessiblePaths=/var/lib/keybox`) and `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6`. The OS is Ubuntu LTS minimal with unattended security upgrades (cloud-init, `KBOX-48`). Test (`test/deploy-units.test.ts`, text check of `deploy/*.service` and `deploy/keybox-tmpfiles.conf`, and a started-process check in `test/journeys/process-split.test.ts` that uses two stand-in listener scripts for core and relay, so it needs no later unit; the real relay joins in `relay`'s journey): each directive, directory mode, owner and group is present; with the real modes, the relay uid cannot `connect` to `/run/keybox/http.sock` and cannot list `/run/keybox`, the caddy uid cannot `connect` to `lend.sock`, the relay uid can, and the relay process cannot open a vault file; a socket created in each directory has the directory's group; the lend socket exists only after core starts. The uid-switch half needs root: the gate runs this one file as `sudo -n node --test test/journeys/process-split.test.ts` with `KB_REQUIRE_UIDSWITCH=1`, and with that variable set a test that cannot switch uid **fails**. The three uids come from the test itself, so nobody else has to provide them: as root it creates any of the three system users `kbt-caddy`, `kbt-keybox`, `kbt-keyrelay` that are missing (`useradd --system`, no login shell), uses only those, and its teardown deletes only the ones it made; a missing `useradd` or a failed create fails the test (owner: unit `kernel-store`); the directory text check also covers `/etc/keybox` and `/var/lib/keybox-install` (root, 0755); without the variable the test reports a skip as "unverified", never green, and the builder's report says so.

**`KBOX-50` The audit log is append-only and hash-chained, and never holds a value.** Source: design §1.1. Rows `{seq, at, actor, action, ref, detail,
prev_hash, hash}` with `hash = SHA-256(prev_hash ‖ canonical JSON of the row without hash)` (canonical JSON as in `KBOX-9`). The first row's `prev_hash` is 32
zero bytes. `actor` is a token label, an approver id or `box`. `detail` is a closed object per action (names, ids, codes, statuses, byte counts). The port
has `append` and read only; there is no update or delete path. A relay row (`KBOX-13`) carries time, token label, source address, claimed agent and project,
keyref, method, rule id, status, bytes. Test: appending 1,000 rows then flipping one byte of a stored row makes `verifyChain()` name the first bad `seq`;
a deleted row is detected; `detail` objects with an unknown member are refused at the writer; the canary is absent; two concurrent appends get distinct
sequence numbers and a valid chain.

### Unit `kernel-approve`: approvers, approvals, slots, phone pages, recovery and push

**`KBOX-49` First approver: the setup code and the phone's registration.** Source: design §1.5 steps 4 and 5. At first start with no approver, the bootstrap (root, `KBOX-48`)
creates a one-time setup code (12 words, 132 random bits from the 2048-word list `src/data/wordlist.txt`, BIP-39 English; decided here), keeps only its root-owned hash in `/etc/keybox/codes/setup.hash`
(SHA-256 of the lower-case words joined by single spaces; core cannot read it) and writes the words only to the console sink (`KBOX-20`'s sink, never stdout or the journal). `/setup` on
`keys.<domain>` takes the code, then runs one page flow: create a passkey (WebAuthn `attestation: "none"`, ES256 only, user verification required), create the
device key (`KBOX-9`) with the loss warning shown first, subscribe to Web Push (`KBOX-22`), and type a short phrase. Setup then closes for good: with one approver
registered `/setup` answers 404. Completing setup relays the code with the approver's public keys to `kb-install`, which checks the code itself and accepts it only while `/etc/keybox/trust.json` does not exist (`KBOX-6`), and so writes the first `/etc/keybox/trust.json` (the domain and the approver's public keys, `KBOX-6`), through the `TrustPort` declared in `src/ports/trust.ts` (kernel-approve; the real port is built by `update`, tests use a fake): setup is not complete until the result is `applied`. Later approvers come only by approval (`approver_add`, `KBOX-53`) or by recovery (`KBOX-20`). The only CBOR the box parses is
one COSE public-key map at registration: a decoder for exactly EC2 P-256 ES256 (small-integer keys; integer and byte-string values) that refuses anything
else. Test (`test/setup.test.ts`): core cannot read the setup code hash (file mode); `setup` is refused by root once `trust.json` exists, even when core says the code is valid; the code never appears in core's journal or database (canary); wrong code refused and the code stays valid; a second setup refused after the first completes; the code never appears in
captured stdout or the journal; a COSE map with an unknown key type, an extra member, a floating-point value or trailing bytes is refused; setup without a
device-key registration refuses to complete; setup calls the fake `TrustPort` with the domain and the approver's public keys and does not complete on a refused answer; the phrase is stored in `private.db` only.

**`KBOX-7` What needs the phone: one approval per action, bound to one exact action.** Source: design §3. The actions that need an approval: adding or
importing an admin or master key, deleting one, every rotation of one (scheduled or manual); granting or revoking a machine's use of an admin key; adding or
removing a destination of an admin key, and changing its relay allow rules or schedule; lowering a key's class (`demote`); enrolling a machine token; a Vercel
domain or team-setting change (`KBOX-26`); adding or removing an approver; installing an update. Changes to ordinary keys need no approval. There is no bulk
approval route and no route that takes more than one action. **Slots (against approval fatigue):** every proposal, and every paste task (`KBOX-12`: the paste is the approval of an `add_key` or `rotate_key`), sits in one slot named by kind and subject. `add_key`: the platform; `delete_key`, `rotate_key`, `demote`, `set_allow_rules` and `set_schedule`: the key; `grant` and `revoke_grant` share the slot `grant`, and `add_destination` and `remove_destination` share the slot `destination`, each with the key as subject; `enrol`: the source address; `vercel_set_domain`: project and operation; `vercel_set_team_setting`: the setting name; `approver_remove`: the approver id; `approver_add` and `install_update`: no subject and one slot each. A paste task occupies the slot of its own action, expires after 14 days like any proposal and sends one push per slot (a same-token replacement sends none). Proposals created by `POST /api/enrol` (no token) share one push while any of them is unseen; the push says only how many wait. `approver_remove` naming the last approver is refused with `rejected`. One proposal is pending per slot. A
second proposal in an occupied slot from another requester token is refused with `slot_taken` (409) naming the pending approval; from the same requester token
it **replaces** the pending content (same approval id, `revision` + 1, new digest, fresh nonce, the earlier assertion no longer applies) and sends no new push;
a proposal originated by the box (a scheduled rotation, a platform expiry) takes over an occupied slot; pending proposals expire after 14 days; a denial
frees the slot. A proposal that would allow a `mustDeny` operation (`KBOX-25`) is refused at proposal time with `rejected` and never reaches the phone. The
scheduler's one-per-day staggering is in `KBOX-52`. Test (`test/slots.test.ts`, `FakeClock`): every row above as a case, one test per kind including `add_key`, `revoke_grant`, `remove_destination`, `approver_remove`, `vercel_set_team_setting` and a paste task; five `add_key` proposals with different names on one platform give one pending approval and one push; a paste task occupies the `add_key` slot and expires at 14 days; 50 unauthenticated enrol requests from 50 addresses give 50 proposals and one push; `approver_remove` of the last approver refused; update, approver-add, enrol (per source
address) and demote (per key) each have one slot; a second token gets 409 and the same token replaces with no second push; a box rotation takes over a squatted
slot and the squatter's pending assertion no longer applies; expiry at 14 days minus 1 ms and plus 1 ms; denial frees; no route accepts a list of actions; a
canary in a requester reason is absent from push payloads.

**`KBOX-8` The box writes the words.** Source: design §3. The action is stored as typed data when proposed. The page text is rendered by the box, in fixed
sentences per action kind (`src/pure/words.ts`), from that data, never from text sent by mission control. A requester's reason appears separately as "Reason

**`KBOX-9` The signature is bound to the exact action and to the approver device.** Source: design §3. `actionDigest = SHA-256` of the canonical action JSON,
which is RFC 8785 (JCS) restricted to integers: sorted keys, UTF-8, no floats, no `null` (an absent member is omitted), no whitespace. Each page render gets
a fresh 32-byte nonce, used once. The challenge is `SHA-256("kbox-v1" ‖ approvalId ‖ actionDigest ‖ nonce)` (approvalId as UTF-8; the digest and nonce are
fixed length, so the concatenation is unambiguous). The box accepts an approval only when all hold: the passkey signature verifies against a registered
approver; `clientDataJSON.type` is `webauthn.get`; the origin is exactly `https://keys.<domain>`; `rpIdHash` is SHA-256 of `keys.<domain>`; flags UP and UV
are set; the challenge matches; the nonce is unused; the stored action is still pending with the same digest; and an ECDSA P-256 signature over the same
challenge verifies against **the device key of the same approver** (WebCrypto non-extractable key, signature as raw 64-byte r‖s over the 32 challenge bytes
with SHA-256, verified with `dsaEncoding: 'ieee-p1363'`). An approver is a (passkey, device key) pair registered together. A passkey alone never approves or
opens a view. An approval executes by its stored id, never from a client body. The nonce, `authenticatorData`, `clientDataJSON` and both signatures of an approved `install_update`, `approver_add` or `approver_remove` are kept with the approval, because the root installer verifies them again itself (`KBOX-6`); `src/pure/{webauthn,cose,challenge}.ts` is the one verifier, imported by core and by `kb-install`. Deny needs an assertion and a device-key signature too, over `SHA-256("kbox-v1-deny" ‖ approvalId ‖ actionDigest ‖ nonce)`, so an approval proof cannot deny and a denial proof cannot approve (an approval's proof, kept for the root installer, stays over the `kbox-v1` challenge). A **view session** needs the passkey assertion
and the device-key signature over a view challenge `SHA-256("kbox-v1-view" ‖ nonce)`, and gives a read-only cookie (`__Host-` prefix, HttpOnly, Secure,
SameSite=Strict, no `Domain`) that can change nothing: every state-changing route refuses a request that carries only the cookie. A **signed operation** is a phone action that changes state at once and is not the approval of a stored action: `enrol_window_open {label}` and `token_revoke {label}`. It needs the passkey assertion and the device-key signature over `SHA-256("kbox-v1-op" ‖ SHA-256(canonical operation JSON) ‖ nonce)` (a fresh single-use nonce from the page render, as for an approval). Losing the device key (reinstalling the app, clearing its data) forces recovery; the setup page says so
before it creates the key. Hand-written crypto here (WebAuthn assertion verification, authenticator-data parsing, DER-to-raw ECDSA conversion, challenge
construction) uses `node:crypto` primitives only and has known-answer tests. Test (`test/approval-binding.test.ts`): an assertion for action A replayed for B is
refused; UV clear refused; wrong origin and wrong rpIdHash refused; `type` other than `webauthn.get` refused; nonce reuse refused; passkey without device
signature refused; passkey of approver X with the device key of approver Y refused; a changed action digest after render refused; for an approved `install_update` the stored proof holds the fields `kb-install` needs and a proof stored for A cannot be re-attached to B; a view session without the
device signature refused; a signed operation without the device signature, with a replayed nonce or for another label refused, and the view cookie alone refused on every state-changing route; the assertion verifier passes a WebAuthn assertion vector committed in `test/fixtures/webauthn/` with its source named in `SOURCE.md`: a published vector or, if none is usable, one made by an independent implementation (a Python `cryptography` script kept beside it, run once, not in the suite), never one made by `softAuthenticator()`; the test **fails** when the fixture is missing; a
JCS vector set (sorted keys, unicode, escapes, integer boundaries, a float refused).

**`KBOX-11` Machine tokens and their scopes.** Source: design §2 (owner decisions C-686). A token is generated on the machine that uses it: the machine's
enrol step writes 32 random bytes to its local store and sends only `SHA-256(token)`, a label and the scope. Passes are not tied to an address: no address is
registered, pinned or checked; the box writes the client address of every use to the audit log. The first enrolment (mission control's `control` token) is
accepted only inside a 10-minute window the owner opens in the app for one label, by a **signed operation** (an assertion plus a device-key signature, `KBOX-9`; the view cookie alone cannot do it). The `control` enrol must carry that label and the window takes one enrol. Every later enrolment is a proposal and needs

**`KBOX-6` The box installs only an approved exact hash, over the base it was approved against.** Source: design §1.4. `POST /api/updates` (scope `control`,
`Content-Type: application/x-tar`, query `commit=<40 hex>`) takes a tar of the tracked files at commit C plus `runtime.lock`. Intake limits: 20 MiB, 5,000
entries, 255-byte paths; regular files and directories only; symlinks, hard links, devices, FIFOs, pax or GNU extended headers and any path outside the tree
(absolute, containing `..`) are refused; so is a duplicate path, a path with a NUL, a newline or any other control byte, a backslash or invalid UTF-8 (a newline would make the hash text ambiguous). One pax **global** header (`g`) as the very first entry is accepted and ignored (that is how `git archive` writes
the commit id; decided here). The box computes the **content hash** H itself: SHA-256 of the text made of one line per file, sorted bytewise by path,
`<mode> <sha256 hex> <path>\n`, with mode `0755` if the owner-execute bit is set and `0644` otherwise (decided here). It opens an `install_update` approval
`{install: H, commit: C, base: H0}` where H0 is the running release, and answers 201 `{approval_id, hash, base}`. The phone page says, in the box's fixed words:
"Install key box version H[:12] (commit C[:12]) over version H0[:12]"; the number of files added, changed and removed; changes to `runtime.lock` (Node or Caddy
binary hashes) with the official download URL of each; and the fixed sentence **"Agents wrote this version and only agents checked it. Any change can take every
key, and this page cannot tell whether it is safe."** Core (user `keybox`, `NoNewPrivileges`, `ProtectSystem=strict`) writes nothing under `/opt/keybox`. It keeps the intake tree in its own `/var/lib/keybox/staging/<H>/` and downloads any new pinned binary to `/var/lib/keybox/staging/<H>.bin/<name>`. **Where the binaries are:** the Node and Caddy binaries are not in the tar and not in H; `runtime.lock` is a tracked file inside the tar, so H covers each binary's pinned sha256, and `kb-install` checks every binary against the copied lock on every install (a binary whose pinned hash equals the one in the running release's lock is taken from `/opt/keybox/current` and a new one from `<H>.bin`; both are read through the safe open below, hashed, and compared, so an unchanged binary is re-verified, not trusted). On approval core checks that `current` is still H0 (else a new proposal is needed) and writes one request `/var/lib/keybox/staging/<H>.request` by temp file and rename: `{kind:"install", install:H, commit:C, base:H0, approval:<proof>}`, where `<proof>` is what the phone sent for this approval (`KBOX-9`): approval id, approver id, nonce, `authenticatorData`, `clientDataJSON`, the passkey signature and the device-key signature. Core keeps these with the approval; they are public data and hold no value. **The privileged installer is `kb-install`**: a root `Type=oneshot` unit started by `kb-install.path` (`PathExistsGlob=/var/lib/keybox/staging/*.request`), with `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ReadWritePaths=/opt/keybox /var/lib/keybox/staging /etc/keybox /var/lib/keybox-install`, `PrivateNetwork=yes`, `TimeoutStartSec=120s` and, on the service and the path unit, `StartLimitIntervalSec=0` (a trigger is never refused, and a run always removes what triggered it, below). Its code runs from the **running** release, never from the bundle being installed: at start it resolves `realpath(/opt/keybox/current)`, loads every module it will need before doing anything else (static imports only; a dynamic `import()` in `src/cli` and the modules it imports fails the arch test) and uses the resolved path to the end, so a rollback after step 5 never loads code from the new release.

**The root copy of the approvers.** `kb-install` takes the approver public keys and the domain from `/etc/keybox/trust.json` (owner root, 0644, in `/etc/keybox` root 0755, both made by `deploy/keybox-tmpfiles.conf`; `{domain, approvers:[{id, cose_b64, device_pub_b64}]}`, public keys only). Only `kb-install` writes it, by temp file and rename. Core's own approver table is never consulted. A `trust` request `{kind:"trust", change, approval|code}` changes the file: `approver_add` and `approver_remove` carry a proof of the approved `approver_add` or `approver_remove` action, verified as below against the file as it stands, and core changes its own table only after `kb-install` reports the change applied (a refusal makes the approval `rejected`); `setup` (accepted only while the file does not exist: the first approver and the domain) and `recovery` (replaces every approver) are made when `KBOX-49` and `KBOX-20` complete. For `setup` and `recovery` the proof is a code that **root** made and checks: `{kind:"trust", change:"setup"|"recovery", code, approvers}`, where core only relays the code the owner typed with the new approver's public keys. Root keeps only the hash of each code in `/etc/keybox/codes/` (root 0700, so `keybox` cannot read the hash or list the directory; files `setup.hash` and `recovery.hash`, the latter with its `boot_id` and write time), compares the hash itself, refuses a recovery code older than 30 minutes, from an earlier boot or used before, accepts a `setup` code only while `trust.json` does not exist, and deletes the hash on use. Core never sees either hash and cannot change `trust.json` without a code root checks; core's own table follows only after `applied`. The codes are made by the root side (`KBOX-20`, `KBOX-49`), not by core. Code tests in `test/install-helper.test.ts`: core's uid cannot read or list `/etc/keybox/codes` (file mode); a `recovery` request with a wrong code is refused by root even when the request says core found it valid; `setup` is refused once `trust.json` exists; a used code is refused.

**Its own proof of approval.** `kb-install` never takes core's word that an approval happened. For an `install` request it rebuilds the action `{kind:"install_update", install:H, commit:C, base:H0}` from the request's fields (H being the hash it computes itself, below), computes `actionDigest` and the challenge as in `KBOX-9`, and itself verifies every condition of `KBOX-9` that does not need core's state: the passkey signature against an approver in `trust.json`, `clientDataJSON.type` `webauthn.get`, origin `https://keys.<domain>` and `rpIdHash` from the root copy's domain, flags UP and UV, the challenge, and the device-key signature of the **same** approver. It uses the same `src/pure/{webauthn,cose,challenge}.ts` as core (one home), loaded from the running release. A request with no proof, a malformed or invalid proof, a proof by an approver not in `trust.json` (removed or never copied), or a proof for another H, commit or base is refused before anything is copied. Nonce use and the pending state stay core's checks; replay is closed by the base check and by the request working once.

**The safe copy.** Everything in `/var/lib/keybox/staging` can be changed by `keybox` at any moment, so `kb-install` trusts no path, only what it holds open. It opens the staging root with `O_DIRECTORY|O_NOFOLLOW` and every entry relative to the descriptor of its parent (Node has no `openat`; the path `/proc/self/fd/<n>/<name>` resolves through the held descriptor, and that it works under `ProtectSystem=strict` is UNVERIFIED and probed on the real instance), each with `O_NOFOLLOW|O_NONBLOCK`; `O_NONBLOCK` is why a FIFO does not block the open. It `fstat`s each descriptor: only a regular file or a directory is accepted, anything else (symlink, FIFO, socket, device) is refused `not_regular`. It reads each file **through the descriptor** into memory, hashes the bytes it read (sha256 per file; H is computed from these hashes, not from a second read of any path), and writes the same bytes into root-owned `/opt/keybox/releases/<H>.tmp` (created `O_EXCL`; owner root, files 0644 or 0755, directories 0755, nothing writable by `keybox`). It reads at most the `fstat` size plus one byte and refuses (`size`) a file whose bytes read differ from that size, so a file that grows is caught. It re-applies the intake limits and name rules to the tree it reads (20 MiB in all, 5,000 entries, 255-byte names, no control byte, backslash or invalid UTF-8, regular files and directories only), so the checks at intake are not the only ones. The copy has a deadline of 60 s (`timeout`; the unit's `TimeoutStartSec` is the backstop), so nothing `keybox` does can hang the oneshot.

**The steps**, after the request is read (through the same safe open, at most 64 KiB) and **unlinked at once** (unlink never follows a symlink; a request works once): (1) refuses if `current` is not H0, or if H is H0 (`already_current`); (2) removes any stale `releases/<H>.tmp` and any `releases/<H>` that is not `current` (a retry of a rolled-back H works), then makes the safe copy; (3) takes H from the bytes it read, refuses on mismatch with the H the approval named, and checks each binary as above; (4) renames `<H>.tmp` to `<H>`; (5) switches `current` by creating a temp link and renaming it over the old one; (6) restarts the three units. The bytes installed are exactly the bytes that were hashed. The health check passes when both processes answer `GET /healthz` with the new H within 60 seconds of restart (decided here); on failure `kb-install` switches back to H0, restarts, removes `releases/<H>` and reports `rolled_back`. **Results:** `kb-install` writes `/var/lib/keybox-install/<name>.result` (a root-owned directory `keybox` can read and not write, so there is nothing to pre-plant; made by unlink then `O_CREAT|O_EXCL|O_NOFOLLOW`) with a fixed code: `installed`, `rolled_back`, or `refused:<code>` (`no_proof`, `bad_proof`, `base`, `already_current`, `not_regular`, `hash`, `lock`, `size`, `timeout`); core emits `update.state` from it. Every run removes **every** entry in staging matching `*.request`, whatever its type (a directory is removed without following any link inside), so a pre-planted directory, symlink or FIFO named `x.request` cannot keep the path unit triggered; a refusal exits 0 (a decided outcome, not a unit failure). An approval names H and H0 and cannot install any other bundle or apply over any other base. **What an update cannot change:** the unit files, `deploy/keybox-tmpfiles.conf` and `deploy/Caddyfile` come only from the bootstrap (`KBOX-48`); the bundle holds copies, but `kb-install` installs nothing outside `/opt/keybox/releases`, `/opt/keybox/current` and `/etc/keybox/trust.json`, so hardening changes need the bootstrap redone on the instance through the Oracle login (the same road as `KBOX-20`).
Test (`test/update.test.ts` for intake and approval, `test/install-helper.test.ts` for `kb-install`, both with temp dirs and a fake systemd port; the helper test has a hook between copy and hash): staged tree changed after approval refused; a staging file changed **during** the copy is caught because the hash is over the copy; a request naming H while staging holds H2 refused; a request replayed after success refused; a symlink in staging refused; ### Unit `relay`: the relay process, the lend socket, forwarding, scanning and the egress gate

**`KBOX-3` Master keys never reach the relay.** Source: design §1.2. kb-relay cannot read the vault. Core lends it a value over `/run/keybox-lend/lend.sock` (one request
per lend; request `{token_hash, keyref, rule_id, project?}`, `project` present exactly when the key's profile has a `project-host` origin and refused (`forbidden`, audit code `location_mismatch`) unless it equals the key's stored project (`KBOX-57`); answer the value for that one call) only when all hold: the key is admin class (never master, never
ordinary), a grant exists for the calling relay token's machine, the key has a relay profile, and the request matched an allow rule of that profile. Core
re-checks token, grant and rule id. Master values are lent only to issuer, verifier and destination code inside core. This is enforced by a class check in the
lend handler, not by configuration. Indirect use is closed by `KBOX-13` and `KBOX-14`. Test (`test/lend.test.ts`): a master keyref is refused with no value
sent; an ordinary keyref refused; a keyref without a grant refused; a revoked token refused; a rule id not in the profile refused; a lend call from a process
the socket mode refuses (see `KBOX-45`); the lend response is a one-shot (a second read on the same connection gets nothing); core down makes the relay answer
503 `unavailable`; the canary is absent from the relay's logs.

**`KBOX-13` Forwarding rules.** Source: design §4. The relay URL is `https://api.keys.<domain>/r/<keyref>/<path>`; the upstream origin is fixed by the key's
profile (a `project-host` profile, Supabase, sends to `<ref>.<domain>` where the ref is the key's stored project from core's resolve answer and nothing else, `KBOX-57`; the Google profile takes the host as the first path segment, which must equal byte for byte one of the key's declared hosts: lowercase ASCII, no
port, no `@`, no `%`, no trailing dot). In order:
1. Read the caller's token from the profile's declared headers (`Authorization: Bearer`, `apikey`); if several declared headers are present they must carry
   the same token or the request is 400.
2. The token must be a relay token, not revoked, with a grant on `keyref`; the source address is not checked, it goes in the audit.
3. **Parse once, refuse ambiguity.** From the raw request target, 400 with no upstream call if the path has an encoded `/`, `\` or `.` (`%2F`, `%5C`, `%2E`,
   either case); `%00`, a control byte or a non-ASCII byte; a raw `\`, `;`, `#`; an empty segment (`//`); a `.` or `..` segment; a malformed `%` escape. The
   remaining percent escapes are decoded per segment; rules match the **decoded segments**; the forwarded path is the decoded segments re-encoded canonically
   (RFC 3986 unreserved characters and the path characters `:` and `@` literal, everything else `%XX` upper case), so the path matched is the path sent.
   `:` stays literal because Google routes custom methods only on a literal colon: `documents:runQuery` reaches the method while `documents%3ArunQuery`
   is a 404 like a made-up verb (probe `google.colon-encoding`, 2026-11-12). A rule naming a literal `:` segment therefore matches a request that sent `%3A`
   too, and the request forwarded is the one the rule names.
4. **Method and query.** The method comes from the request line only; `X-HTTP-Method-Override`, `X-HTTP-Method`, `X-Method-Override` give 400. The query is split on
   `&`; 400 for a malformed `%` escape, `%00`, a control or non-ASCII byte, a raw `;` or `#`, an empty key or a duplicate key; names and values are decoded once
   and a decoded name or value still holding `%`, `&`, `=` or a control byte is refused. Each allow rule lists the exact query keys it accepts, each with a value
   shape (a fixed word or a bounded integer); the default is none. A decoded key the matched rule does not list is 403, so `?al%74=media`, `?%24method=`,
   `?%61ccess_token=` and `$httpMethod` fail and no rule lists `access_token`, `key` or `apikey`. The forwarded query is the matched keys re-encoded.
5. **Match the profile**: default-deny; the request must match one allow rule `{id, method, host, pathTemplate, query}` and none of the profile's `mustDeny`
   rules. A miss is 403, no upstream call, no lend.
6. Ask core for a lend (`KBOX-3`).
7. Build the upstream request: forward only the profile's request-header allow-list (default `Content-Type`, `Accept`, `Content-Length` recomputed; per profile
   `Prefer`, `OpenAI-Beta`, `Idempotency-Key`; Supabase `Accept-Profile` and `Content-Profile` only with the value `public`); drop everything else
   (the caller's `Authorization` included). **No partial-content header is ever forwarded**: `Range` and `If-Range` are on no profile's list (the registry check of `KBOX-23` fails startup if any profile lists one), so the caller cannot make upstream answer with a piece of a body; no allow rule may list a query key whose only job is to cut a response to a size or an offset (decided per rule at review; the scanner's cut-stream rule in `KBOX-14` is the backstop). **Trailers are dropped** in both directions: request trailers are not forwarded (the upstream request is sent with none), and response trailers never reach the caller (the scanner cannot see them, so none is passed). Upstream traffic is HTTP/1.1 only (no `h2` ALPN, so no multiplexed or trailer-bearing framing); Caddy to relay is HTTP/1.1 over the unix socket. Set `Accept-Encoding: identity`; set the profile's auth headers from the lent value, never in the query or body; `redirect:
   manual` (a 3xx goes back unfollowed); send through the egress gate (`KBOX-47`); stream both ways (SSE works); request bodies up to 32 MiB (413 above).
   The upstream connect timeout is 10 s and there is no total timeout, so streams are not cut (decided here).
8. Pass the response through the scanner (`KBOX-14`).
9. Audit (`KBOX-50`): time, token label, source address, claimed agent and project (`X-Agent`, `X-Project`; logged, not checked, not forwarded), keyref, method, **rule
   id** (the query is dropped), status, bytes. Bodies are never logged. WebSockets are not relayed in v1.
Failure shapes: unknown or revoked token 401 `bad_token`; no grant or no rule 403 `forbidden`; ambiguity 400 `bad_path`, `bad_query`, `method_override`; upstream
unreachable 502 `upstream_unreachable`; connect timeout 504 `upstream_timeout`; core down 503 `unavailable`; each with the fixed text of `KBOX-29`'s frame.
Test (`test/relay-forward.test.ts`, relay over a real loopback `fakePlatform()` through the gate's test connector): the canonicalisation table (`%2F`, `%2e%2e`,
`//`, `;x`, `\`, non-ASCII, bad `%`, `/v1//x`, `/v1/%6Frganization/`) gives 400 with no upstream call; the forwarded path equals the matched path; the three override
headers give 400; `?_method=`, `?al%74=media`, `?%24method=`, `?%61ccess_token=`, `$httpMethod`, a duplicated key give refusal with no upstream call; a non-listed request
header is not forwarded and the caller's `Authorization` never is; a caller's `Range: bytes=0-9` and `If-Range` reach the fake upstream as no header (the upstream's request log shows neither); a request with a trailer is sent upstream with none; a profile listing `Range` fails the registry check; the upstream connection negotiates no `h2`; `Accept-Profile: vault` gives 403; a 3xx is not followed; a granted master keyref gives 403 with no upstream call; two different source addresses both pass;
the audit row has the rule id and no query; a hung upstream gives 504; a refused connection gives 502; the real streaming path is run once end to end with a 5 MiB
body and an SSE stream.

**`KBOX-14` Response handling.** Source: design §4. Every relayed response's headers and body are matched, as a stream with carry, against every value the box holds
(all `scanForms` of `KBOX-54`, master values and the short-lived Google tokens the relay injects included) and against a fixed list of credential shapes held as data in
`src/data/credential-shapes.json`: prefixes `sk-`, `sk_`, `rk_`, `ek_`, `vcp_`, `vci_`, `vca_`, `vcr_`, `vck_`, `sb_secret_`, `sbp_`, `GOCSPX-`, `AIza`, `ya29.`, `1//`,
`github_pat_`, `ghp_`, `whsec_`; PEM private-key headers; JSON members named `private_key`, `client_secret`, `refresh_token`, `access_token`, `bearerToken`,
`signing_secret`, `xi-api-key` or `api_key` with a non-empty string value; JWTs (three base64url segments, the first decoding to JSON with `alg`). On either hit the
stream is cut, the caller gets 502 `withheld` ("response withheld: it carried a key"), and the audit log and an owner notice follow; there are no per-operation
exceptions. **No part of a match reaches the caller before the cut.** The scanner releases a byte only when it cannot belong to a match. **The hold-back is counted in the same stripped view the matcher matches in** (`KBOX-54`: line breaks and the `\`-newline pattern removed): it holds back the last (longest `scanForms` form minus 1) **stripped characters**, and every raw byte from the raw offset of the first of them on, the removed line-break bytes between and after them included, so a base64 copy wrapped at 64 or 76 columns with CRLF cannot have its start released before the copy completes. Credential candidates are found in the stripped view too. **Candidate rules** (data in `src/data/credential-shapes.json`, one entry per shape): a listed prefix opens a candidate where it appears; the candidate is **decided a credential** when at least `min` characters of its `alphabet` follow the prefix (default `min` 20 and alphabet `[A-Za-z0-9_.~+/=-]`; `AIza` 35 and `GOCSPX-` 28, the lengths of those formats, UNVERIFIED and checked by the adapter probes), and **decided not a credential** at the first byte outside the alphabet before that, so prose such as `task-` or `sk-ill` is released at once and the hold is never longer than `min` plus the prefix; a PEM header is decided by the whole `-----BEGIN … PRIVATE KEY-----` line; a listed member name is decided at the closing quote of its value (non-empty is a hit); a JWT candidate (`eyJ`) is decided at the first `.`: a hit when the first segment decodes to JSON with `alg`, otherwise released, and a first segment longer than `jwt_header_max` in the data file (512; a header is a few dozen characters) is not a JWT header and is released, so a long base64url run is never held without end. Everything from the start of an undecided candidate is held. A candidate that proves not to be a credential is released. **Partial content:** a 206 response, or any response carrying `Content-Range`, is refused with 502 `withheld` before any body byte is sent, audit reason `partial` (the request side forwards no `Range`, `KBOX-13`). One exception, for a relay profile that sets `itemsRange` (Supabase: PostgREST states the rows of every 200 read as `Content-Range: 0-24/*`, a count of whole rows, not bytes): a 200 whose `Content-Range` is exactly `<first>-<last>/<total>` or `*/<total>` (`<first>`, `<last>` digits; `<total>` digits or `*`; no unit word) passes, and the header is still not sent on (it is not on the allow-list); any other form, a `bytes` unit, or a 206 is refused as above (revision 2026-11-12: without the exception every PostgREST read was withheld; the body is still scanned whole, and the caller still cannot ask for a range). **Cut streams:** at a clean end of stream (the HTTP layer saw the full declared length or the terminal chunk) the held tail is scanned and then released; when the stream is cut for any other reason (upstream reset, premature close, fewer bytes than `Content-Length`, a chunked body with no terminal chunk, a timeout, the scanner's own cut) the held tail and every undecided candidate are **discarded, never released**, so a cut stream ends with no tail and the caller gets no partial prefix. A copy that upstream itself truncates and then ends cleanly, with no caller input (no `Range`, no 206), is not matched (a stated limit: the caller then holds a prefix that upstream chose to send, not one the box or the caller added). Response trailers are dropped (`KBOX-13`). **Encoding:** the request sets `Accept-Encoding: identity`; a response whose `Content-Encoding` is anything but absent or `identity` (a stacked list included) is refused with 502 `withheld` before any body byte is sent, audit reason `encoded`, because the scanner cannot see inside it (refused, not decoded: no decompressor in the trusted path); `Transfer-Encoding: chunked` is decoded by the HTTP layer before scanning. Upstream 401 and 403 bodies are replaced by the fixed text "upstream refused the key" with the status. Response headers are an allow-list (`Content-Type`,
`Content-Length`, `Retry-After`, rate-limit headers, `Location` on a 3xx, the platform's request-id header); `Set-Cookie` is dropped; every response gets
`X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox; default-src 'none'` and `Content-Disposition: attachment`. Test (`test/relay-scan.test.ts`): a
held value withheld in raw, base64 (three alignments), hex, percent, JSON and `\u` forms, split across two chunks and across the header and body; a `sk-…`, a JWT, a
`"client_secret":"x"` and a PEM withheld; an empty-string `api_key` member passes; an upstream 401 whose body quotes a key hint is replaced; response headers are exactly
the allow-list plus the three forced ones; the cut stream sends no more bytes after the hit (a byte counter on the fake upstream's socket); the bytes sent to the caller before the cut never include a byte of the planted copy (the sent count is at most the copy's start offset), for a held value in each form, a `sk-` key, a JWT and a `client_secret` member, at every split of a seeded chunking; a decoy that starts like a credential and stops is released whole; **wrapped copies**: a held value in base64 wrapped at 64 and at 76 columns with CRLF, and with `\`-newline, planted at a random offset and split at every chunk boundary of a seeded chunking, never has a byte of the copy sent before the hit (the sent count is at most the copy's raw start offset; the hold-back is counted in stripped characters, so a raw-byte count of the same length would fail this test), and a wrapped `sk-` key likewise; a 10 MiB run of line breaks inside a JSON string keeps the held bytes below a constant that does not grow with the run (the test reads the scanner's held-byte high-water mark); **candidates**: `task-`, `sk-ill` and `ask-` followed by a space are released whole at once, `sk-` plus 19 alphabet characters then a space is released and plus 20 is withheld, `AIza` plus 34 released and plus 35 withheld, `GOCSPX-` plus 27 and 28 likewise, an `eyJ` run of 600 base64url characters with no `.` is released and, for a 10 MiB such run, the held bytes stay constant (high-water mark), `eyJ…` with a `.` and a header that decodes to JSON without `alg` is released; **partial content**: a 206 from the fake upstream gets 502 `withheld`, audit reason `partial`, zero body bytes sent, and so does any `Content-Range` on a profile without `itemsRange`; on a profile with it, a 200 carrying `0-24/*`, `0-24/25` or `*/0` passes whole with no `Content-Range` sent on, while `bytes 0-24/25`, `0-24` (no total), `0-24/25x`, the items form on a 206, and the items form on a profile without `itemsRange` are refused; **cut streams**: an upstream that sends a prefix of a held value and then resets, closes early, ends a chunked body with no terminal chunk or sends fewer bytes than `Content-Length` gives the caller bytes that stop before the held tail (none of the last (longest form minus 1) stripped characters, and no byte of an undecided candidate), checked in each form; a clean end releases the tail; a response trailer carrying a planted value is not passed; a response with `Content-Encoding: gzip` (body holding the planted value) gets 502 `withheld` with zero body bytes sent, `identity` passes, `gzip, identity` is refused; a seeded property test mixes
random JSON with one planted copy at a random offset and always catches it.

**`KBOX-25` Relay profiles: default-deny, named operations, `mustDeny` regression lists.** Source: design §5.5. A profile's allow rule is `{id, method, host,
pathTemplate, query}`; template segments are literals or typed parameters (`{id:[A-Za-z0-9_-]{1,128}}`); a trailing `{rest:**}` is allowed only where a profile names it
and each tail segment is still validated. A key's own allow set widens only by approval, and the box refuses to propose a rule matching a `mustDeny` sample (`KBOX-7`). "Widens" is meant as `KBOX-61` defines it: the set is a subset of the profile's rules, and any change, including a return to the whole profile, needs the phone.
`mustDeny` is the **regression list**; default-deny is the boundary. Each entry carries concrete sample requests, including the canonicalisation variants of `KBOX-13`.
The deny test sends every sample through the relay with the default profile and with a test profile whose allow set is widened as far as the registry permits, and
expects 400 or 403 and **no upstream call**. The credential-shape scanner is the backstop. The mechanism is built here with a test profile; each platform unit supplies
its profile's content. Test (`test/profile-engine.test.ts`): template matching (literal, typed parameter, `{rest:**}`, a trailing slash, a segment of 129 characters);
widening refusal; the deny test harness itself fails when a sample is allowed (positive control with a deliberately leaky profile).

**`KBOX-23` Registry checks at startup.** Source: design §5.1. The box refuses to start if any fails, and the same checks run as tests: an issuer with
`revealOnce: true` exports a `lister`; a `relay` profile has a non-empty `mustDeny` and no `allow` rule matches any `mustDeny` sample request; no profile's request-header allow-list contains `Range` or `If-Range` (`KBOX-13`); a platform listed in
`relayDenyOnly` (Vercel and ElevenLabs in v1) exports a `mustDeny` list and no `relay`. Adding a platform is one folder `src/platforms/<id>/` plus one registry line.
An entry's `location` declares only `region` and `project`; a `project-host` relay profile's entry declares `project` naming a host, and an entry with a host-naming field has a `locationProver`; a `verifyHints` list has unique `[a-z0-9_]{1,32}` names; each `masterItems` entry is a scope-item prefix ending in `:`; no file under `src/platforms/<id>/` imports `src/platforms/registry.ts` (`RegistryDeps` is in `src/ports/platform.ts`).

**`KBOX-32` The relay endpoint and the pass: what agents and `with-keys` rely on.** Source: design §2, §4; shapes decided here. A pass is a relay token as in
`KBOX-10`, generated on the machine. It is carried in the profile's declared header(s) (OpenAI: `Authorization: Bearer <pass>`; Supabase: `apikey: <pass>`, and
`Authorization: Bearer <pass>`, which supabase-js also sends; Google: `Authorization: Bearer <pass>`). Relay URL: `https://api.keys.<domain>/r/<keyref>/<path>`;
Google: `/r/<keyref>/<host>/<path>`. `GET /r/_/grants` (relay token, carried in `Authorization: Bearer <pass>` or `apikey: <pass>`; both present must be equal, as in `KBOX-13` step 1) returns `{machine, grants:[{keyref, platform, name, projects, env}]}` where `env` is the
profile's `envForClients(relayUrl)` with the pass left as the literal `"<pass>"` (the client substitutes its own pass). The profiles' `envForClients`: OpenAI
`{OPENAI_BASE_URL: <relay>/v1, OPENAI_API_KEY: "<pass>"}`; Supabase `{SUPABASE_URL: <relay>, SUPABASE_SECRET_KEY: "<pass>"}` (relay url is
`https://api.keys.<domain>/r/<keyref>`); Google `{KBOX_GOOGLE_RELAY_URL: <relay>}` (no standard client variable exists; decided here). `_` is not a valid keyref
(`[a-z0-9]{6,24}`). A pass works on `/r/*` only, never on `/api/*`. Test (`test/relay-contract.test.ts`): each profile's env map is pinned; a pass in the wrong header
for its profile is 401; `/r/_/grants` lists only the granted keys of that machine and no value; a keyref of 5 or 25 characters or with an upper-case letter never
routes; a pass for machine A does not list B's grants; the OpenAI SDK's own request shape (an `Authorization` header and a `/v1/...` path under the base URL) is
replayed from a recorded fixture and reaches the matched rule.

**`KBOX-47` The in-code egress gate.** Source: design §1.1, §1.5 (layer 3). Every outbound request of core and relay goes through one module. It refuses a host that is neither declared by a registered
adapter nor listed in `deploy/egress-hosts.json`, a closed data file naming every non-adapter host, its purpose and the one caller allowed to use it: the push-service hosts of `src/data/push-hosts.json` (Web Push, core only) and the download hosts named in the pinned `runtime.lock` (Node and Caddy binaries, core's update intake only). ACME is Caddy's own traffic and not core's. It also refuses any resolved address that is private, link-local or loopback (including `169.254.169.254` and IPv4-mapped IPv6). Resolution happens once and the

### Unit `rotate`: the orchestrator, reconcile, the scheduler, the paste source, key issue and deliveries

**`KBOX-51` The rotation state machine, intent first, reconcile by list.** Source: design §5.2. State per run is persisted in `meta.db`; one run per key at a time
(structural: a unique index). Steps: (1) planned (scheduler, platform expiry, owner or agent request); admin and master keys wait at `awaiting_approval`; (2) write the row
`issuing {run, intentName}` before any platform call, `intentName = kbox_<ref>_g<N>_<run8>` (lower case, valid on every platform; Supabase requires `^[a-z_][a-z0-9_]+$`, 4 to

new key with the verifier that applies to it (`KBOX-58`; none: the step passes) before any push; (6) push to every destination recording a receipt (the platform's object id) per destination, "make it so": a repeat finds its receipt
and updates that object; the workstation destination is a delivery (`KBOX-34`); (7) redeploy where `needsRedeploy` and wait for `ready`; (8) check with that verifier again;
(9) promote: N+1 `current`, N to `grace` until `revokeAt = now + grace` (per key; 24 h by default when any runtime destination exists, else 1 h); (10) end N at the platform: `Issuer.revoke(platformKeyId)` for a generation the box made; for a pasted generation (no platform key id) the entry's `retirer` finds the live key by the old value and ends it; on a platform with neither, the owner ends it (the step-10 notice of `KBOX-17` with reason `owner_ends`, words "End the old key on <platform>; the box watches for it to stop working."),
then **confirm it is dead** before marking it `retired`: a 404 (`absent`) is not proof; the confirmation is the verifier **rejecting the old value** (the vault still holds it),
or, where no verifier of the platform applies to the key, or one applies but the vault no longer holds the value (`KBOX-58`; never because one that applies cannot be reached), the `KeyLister` showing the id absent or disabled in the region and project recorded with the key; if the
verifier says the old value still works or cannot be reached, the key stays in `grace` and step 10's failure path applies. The old value stays in the vault for fingerprints
only until it is revoked (its value file is then deleted, `KBOX-33`), and is never lent or pushed again. **Reconcile** on start and daily: a run holds a **lease** while a process works on it; reconcile skips leased keys, and on start runs
only after resume has re-leased unfinished runs; for every issuer it lists the platform's keys (a lister without a platform-wide `list`: once per distinct stored location of the platform's keys, with each master covering it; a `kbox_…` key in a place no stored key names is not found); a `kbox_…` key matching an unleased `issuing` intent with no stored generation is an
orphan from a crash between steps 3 and 4: it is revoked and confirmed, the run returns to step 2 with a new run id, and the audit log records it; a `kbox_…` key matching no intent or
generation raises one notice. Test (`test/rotation.test.ts`, fakes through the ports, `FakeClock`): a crash injected after each step resumes from the persisted step; crash between
platform create and vault store gives the orphan found by `list` and revoked; revoke returning 404 while the verifier still accepts the old value (wrong-region sample) leaves it

crash is reconciled; a lister with only `listAt` has an orphan at a stored location revoked with the same audit row, lists each stored location once per master, and never lists a box-made key's location; a step-10 stall of a key the box ends itself writes one `rotation.revoke_unconfirmed` row per run, not one per retry; a push repeated after a crash updates its receipt's object and creates none; `overlap: false` order (set new, push, redeploy at once, rollback sets the old value
back); a second run for the same key is refused; a pasted old generation on an entry with a retirer is retired by it and `retired` only after the verifier rejects the old value; a retirer that throws (`ambiguous`) or answers `absent` while the verifier still accepts leaves it `grace` with one notice; an entry with neither gives one `owner_ends` notice and `retired` once the verifier rejects.

**`KBOX-17` Failure keeps the old key.** Source: design §5.2. A failure at steps 3 to 8 rolls back: re-push generation N to the destinations already changed and redeploy those that were
redeployed; revoke N+1 at the platform (if issued) and confirm it as in step 10; mark it `failed`. The owner gets **one notice** per failed run: a Web Push for admin and master keys

**`KBOX-52` The scheduler.** Source: design §5.2. Each key has `rotateEvery` (90 days by default). The due date is the earlier of the schedule and `expiresAt - grace - 1 day`, moved earlier

**`KBOX-12` Phone paste flow.** Source: design §3, §5.3. A paste task appears only in the Key box app's queue (`/p/<id>`); the box never sends a link to it; the page checks the installed app's display
mode as a convenience, not a boundary. For a paste-source key of admin or master class (`KBOX-34`), `add_key` and `rotate_key` open a paste task instead of an approval: the paste, with its assertion, **is** the approval of that one action
(decided here; one action per approval holds). Opening the queue needs a view session (`KBOX-9`) and then shows the owner's setup phrase; the fixed rule on every paste page is **"Only paste where you see
your phrase."** The page names the platform, key, machine grant, scope and location (`KBOX-57`) in the box's words, and, for a key whose platform's verifier applies to it and whose entry has verify hints (`KBOX-40`, `KBOX-58`), a choice of hint (preselected with the stored one on a rotation), with the adapter's own link to the platform's key page (never from mission control), and asks the owner to create
the key on the phone. The value goes in a masked field with autocomplete off; the POST carries the value plus the passkey assertion and device-key signature over `SHA-256("kbox-v1-paste" ‖ pasteId ‖ actionDigest ‖ nonce)`, where `actionDigest` (`KBOX-9`) is the digest of the stored `add_key` or `rotate_key` action (platform, scope, machine grant and `mark_admin` included), shown on the page in the box's words; the POST is refused unless the digest in the challenge equals the stored one, and a same-token replacement of the pending action (`KBOX-7`) makes a new digest and a fresh nonce, which voids the page's assertion.

echoes it. A value failing the shape check is refused for platforms whose format is known; coverage (`KBOX-18`) follows from the shape check only, never from length alone. A failed check shows the verifier's
names-only reason and keeps the field for a retry (HTTP 422 `rejected`). Test (`test/paste.test.ts`): a paste without the device signature, with an assertion for another paste id, with a reused nonce or

(canary); the retry keeps the field; no response contains a URL to the box; the 16 against 32 floor disagreement of mission control's KREQ-14 is not copied: this rule's floor is 16 and the shape check decides
(see open point 2).

The exception, checked first, is a platform whose master the box makes itself (`google`, `KBOX-55`): there a master result is `rejected` (`box_made_master`), because that master is never pasted and a second master would make the box's identity ambiguous. **`KBOX-57` Placement: one stored location per key.** Source: design §5.1, §5.4; decided 2026-11-12. A key's location is where its platform holds it: `{region?, project?}`, platform names only. Each registry entry declares the fields it uses (`location`), each with a full-match pattern, the classes that must name it, and whether it names an upstream host; an entry that declares none takes no location. The phone page of the `add_key` approval and of its paste task shows the location in the box's words; it is part of the action digest (`KBOX-9`).
**Never changed.** The location is stored with the key (`rotation_keys.region`, `rotation_keys.project`). A keyref that exists (a `keys` or `rotation_keys` row) is refused (`conflict`, `key_exists`) by `POST /api/keys` before any approval or paste task, by a settling paste before its verifier is called, and by `create` before its first write; `putKeyInfo` refuses, writing nothing, a row whose stored location differs (`location_immutable`). A key elsewhere is a new key.
**One source.** Every use reads that record and nothing else: `Issuer.issue` gets it as `at` and `Issuer.set` as before. A run is refused before it starts (`rejected`, the codes above) when the stored location fails the entry's current declaration; the schedule skips such a key with one notice per key and code while core runs (a restart may repeat it once): a `box.notice` (`code` the refusal code, text `rotation skipped`) and the audit row `rotation.refused` naming the key, and `POST /api/rotations` answers the same refusal (release 1 registered no platform, so the only such keys are records made by `POST /api/retired`, which takes no location). The issuer reports where the platform says it made the key (`IssuedKey.location`, from the platform's answer, never copied from the request; left out only when the answer names no place, the place then being fixed by the call itself); when present it must equal `at` field for field over the fields either names (a field on one side only is a difference), else step 3 fails (`location_mismatch`), the new key revoked and confirmed at the answered location (`KBOX-17`). Each generation records the location the platform answered (else the stored one) and step 10 confirms against it (`KBOX-51`); the verifier gets it in `VerifyTarget.at`; the relay's upstream host for a `project-host` profile comes only from it (`KBOX-13`, `KBOX-3`). ### Unit `executors-meta`: the frame every approval executor shares, `set_schedule` and `demote`

**`KBOX-60` An approval is executed on the state it finds, once; `set_schedule` and `demote`.** Source: executors design and rulings of 2026-11-13; decided here. Three rules hold for every kind that executes an approval (the frame), then the two kinds this unit builds. The executors live in `src/shell/key-executors.ts`, never in the approval half's own map.

**F1: the executor checks again.** `set_schedule` and `demote` run, before any write, the same checks their proposal made, against the state as it is then (a proposal waits up to 14 days, and another approval or an update can change a key meanwhile). A check that fails records the approval `failed` with the proposal's code (`unknown_key`, `box_made`, `nothing_to_lower`), and `run_exists` is `run_open` there. So `KBOX-55` holds at execution as well as at proposal: a box key's `demote` or its `set_schedule` with `grace_hours` 0 is `box_made` in both places.

**F2: the proposal check.** The same checks run in the approval precheck, beside the box-key refusal (`KBOX-55`), before any approval opens: `rejected` with the code, or `conflict` with `run_exists` for an open run (the code of `KBOX-34`). One function holds each check, so the two places cannot differ.

**F3: an approval that was cut off is not run again.** At start, before core serves, every approval that is `approved` with no result and whose kind has no resume of its own is recorded `failed`, reason `interrupted` (one `approval.executed` event and audit row), and raises one `box.notice` with code `approval_interrupted`, text `approval interrupted` (the approval list shows which approval; the notice names none, like every `box.notice`). The kinds with a resume of their own are left alone: `install_update` (the updater picks it up) and `rotate_key` and `add_key` (their run, if it opened, resumes as a run; an approval row of these kinds that never got its result stays unrecorded, a stated residual). It never calls an executor: a late execution would act on a state the approval never saw (a later approval for the same key, a key re-added under the same reference). The owner asks again.

**`set_schedule {keyref, rotate_every_days, grace_hours}`.** An unknown key is `rejected` (`unknown_key`) at proposal and `failed` (`unknown_key`) at execution. For the box's own key `grace_hours` 0 is `box_made` at both; any other value is allowed. A run open at the time is allowed: the grace is read at promote (`KBOX-51` step 9), so a run that has not promoted yet takes the new grace and one that has keeps its `revoke_at`. Execution writes `rotate_every_days` and `grace_hours` of the key row in one transaction with its `key.changed`, and nothing else: the due date is computed at each tick from the key row (`KBOX-52`), so the next tick uses the new schedule, and `next_due_at` is not touched. Audit `key.schedule_set`.

**`demote {keyref}`.** It lowers what a person controls and nothing else: the owner's mark. Execution clears the mark and recomputes the class as the higher of `classify(scope, {})` and `classify(scope, location)` (`KBOX-15`), so a key never falls below what its scope makes it ("any key that can create keys is `master`"). When that class is not lower than the key's class, there is nothing to lower: `rejected` (`nothing_to_lower`) at proposal, `failed` (`nothing_to_lower`) at execution. A key with an open run (any state before `done`, `failed` or `abandoned`, a grace wait included) is `conflict` (`run_exists`) at proposal and `failed` (`run_open`) at execution: the run was approved for the class the key had. The change is one transaction: the mark, the class, and, when the new class is `ordinary`, the key's grants (fail closed: a key raised again later gets no relay use back without a new `grant`); its allow rules are kept, because `lend` reads an empty set as the whole profile, so dropping them would widen relay use on a later raise. Destinations stay (`KBOX-16`). It ends with the key's `key.changed`. A key that leaves admin and master is no longer in the share file (`KBOX-33`), so the share writer treats a `key.changed` of a key it last saw as admin or master as a change to watch: the next version is written and announced (`version` + 1, one `share.version`). Audit `key.demoted`.

**Audit `detail` schemas (`KBOX-50`, closed):** `key.schedule_set {rotate_every_days: integer, grace_hours: integer}`; `key.demoted {from: ordinary|admin|master, to: ordinary|admin|master}`; the row's ref is the keyref (the approver is on the approval's own `approval.decided` row). **Events (`KBOX-31`):** no new kind; `box.notice` gains the text `approval interrupted`.

**The words** (`KBOX-8`): `set_schedule` keeps its sentence and, when `grace_hours` is 0 and the key has a runtime destination, adds "Apps still holding the old key fail until they redeploy." `demote` keeps its sentence and, when the key falls to ordinary, adds "Machines granted it lose relay use, and the leak check on your workstations stops looking for its value. Its allow rules are kept."; when it falls from master to admin, "It stays an admin key." The page is told the class the key falls to by the same check that decides `nothing_to_lower`.

Test (`test/key-executors.test.ts`, `test/share-file.test.ts`, `test/words.test.ts`): each kind's unknown key at proposal and at execution; the box key's `demote` and a `set_schedule` with grace 0 `box_made` at proposal and, with the proposal check bypassed, at execution; `nothing_to_lower` (an unmarked key, and a marked key whose scope keeps its class); `run_exists` at proposal and `run_open` at execution; `demote` to ordinary drops grants and keeps allow rules, and the share writer's next file lacks the key with `version` + 1 and one `share.version`; `set_schedule` writes `rotate_every_days` and `grace_hours` and one `key.changed`, and the scheduler's next tick uses them; a run that has not promoted takes the new grace; a crash after `approved` committed (an executor that throws once, then a restart): the row is `failed`/`interrupted`, one notice, the executor not called again, and `install_update`, `rotate_key` and `add_key` rows untouched.

### Unit `allow-rules`: a key's own allow set

**`KBOX-61` A key's own allow set narrows its profile; `set_allow_rules`.** Source: executors design section 3 and rulings 2, 7, 8 of 2026-11-13; decided here. A key's own allow set is a subset of the allow-rule ids of its platform's relay profile; the empty set means the whole profile (`lend` reads it so, `KBOX-3`). It never adds a rule the profile lacks: `KBOX-3` lends only for a request that matched an allow rule of the profile, and the profile port has no operation a key could opt into. So `KBOX-25`'s "widens only by approval" means that any change of the set, a return to the whole profile (the empty list) included, needs the phone. The adapter comments that promised a key's rules "may add" (`src/platforms/supabase/relay.ts`, `src/platforms/google/relay.ts`) say this instead.

**`set_allow_rules {keyref, rules}`.** `rules` is `[{op, params}]` (`KBOX-53`); `op` is the id of an allow rule of the key's profile, so the action parser takes an `op` of the shape those ids have (`[a-z][a-z0-9_-]{0,63}`, hyphens included: the real profiles' ids are `gcs-list`, `model-get` and the like, which the earlier `[a-z][a-z0-9_]{0,63}` refused). In v1 `params` must be `{}`: pinning a template value would need the matched values in the lend request, which `KBOX-3`'s `{token_hash, keyref, rule_id, project?}` does not carry, so a non-empty `params` is refused (`params_unsupported`) and the member stays for a later unit. The checks, in this order, are the one function behind both F1 and F2 of `KBOX-60`: the key exists (`unknown_key`); the key is not master (`rejected`, `never_relayed`: a master key is never lent, `KBOX-3`); its platform has a relay profile (`rejected`, `no_profile`; only an update can take one away, so at proposal `KBOX-23` refuses it first); then each rule in order, `params` empty (`params_unsupported`), `op` in the profile (`unknown_op`), `op` not seen earlier in the list (`duplicate_op`). `mustDeny` needs no check of its own: every profile rule already passes the `KBOX-25` deny harness at start, and the set is a subset of them. Proposal answers `rejected` with the code; execution records `failed` with the same code (an update may have removed an op while the proposal waited, so `unknown_op` there). Because ordinary and admin keys may both hold a set (a demote keeps it, `KBOX-60`), only master is refused.

Execution replaces the key's set with the listed ids in one transaction, with the key's `key.changed` (`replaceAllowRules`: a second set removes what the first set held, nothing is appended; the empty list removes the set). A run open on the key does not matter (rules do not touch a run). Audit `key.allow_rules_set` with detail `{count: integer}` (the number of ids now in the set; the ids are in the approval's own action). A set whose ids have all left the profile since it was written is not the whole profile: `lend` refuses every request for such a key (only an empty set is the whole profile). Running it again writes the same state, and a cut-off approval is never run again (`KBOX-60` F3), so nothing here is retried.

**Audit `detail` schema (`KBOX-50`, closed):** `key.allow_rules_set {count: integer}`; the row's ref is the keyref. **Events (`KBOX-31`):** none new; `key.changed` carries the change.

**The words** (`KBOX-8`): a non-empty list keeps "Let the relay pass only these requests with the key <keyref>:" and one line per rule. The empty list reads "Let the relay pass every request the <platform> profile allows with the key <keyref>." (the platform is the first segment of the keyref, as `KBOX-23`'s adapter check reads it) and has no list lines: the older text printed "only these requests:" and nothing under it, which read as the opposite.

Test (`test/allow-rules.test.ts`, `test/words.test.ts`, `test/lend.test.ts`): at proposal each of `unknown_key`, `never_relayed`, `unknown_op`, `duplicate_op` and `params_unsupported` rejects and writes nothing; at execution an op removed from the profile since the proposal fails `unknown_op` and the set is unchanged; a second set replaces the first; the empty list clears the set and one `key.changed` and one `key.allow_rules_set {count}` follow each write; a set whose every id has left the profile lends nothing, over the real lend handler; after a set a lend for a rule outside it is refused and one inside passes; the empty-list sentence and the unchanged non-empty one; every allow-rule id of the three real profiles parses as an `op`.

### Unit `share`: the fingerprint file for the workstation guard

**`KBOX-18` Key formats and watch coverage.** Source: design §5.6. The box computes each key's tier from the real stored value and the adapter's `shape` (prefix, alphabet, core length range, `random`), records it in
metadata and shows it. **Windowed:** a random core of at least 32 characters over an alphabet of at least 16 symbols (so every 24-character window in every shared form holds at least 72 bits); probes use the constant stride and constant probe count of `KBOX-33`, and a windowed core is at most 256 characters (a longer eligible core is `anchored` if it qualifies there, else `none`). **Anchored:** a random core of at least 72 bits (measured core length times log2 of the alphabet size) with a fixed public prefix of at least 4 characters; the matcher finds the prefix's
encoded form then compares an HMAC over the characters that follow which depend on core bytes alone (full-core digests, no windows; it misses copies with the prefix cut off). **Not watched:** everything else, and the approval
page says so. Eligibility comes from the adapter's strict shape check or box generation only, never from a pasted value's length. A UNVERIFIED length can at worst move a key between tiers. Test (`test/coverage.test.ts`):

**`KBOX-33` The share file, format v3: what devbox's `admin-match` reads.** Source: design §6.5, devbox `admin-secrets-spec.md` §3 (v2); layout decided here. The file is one JSON envelope
`{"format":"kbox-share","v":3,"body_b64":"…","sig_b64":"…"}` where `sig_b64` is an Ed25519 signature over the **exact bytes** of `body_b64` decoded, so a reader verifies the signature before parsing and needs no canonicalisation.
The body is JSON `{header, entries, probes, coverage}`:
- `header = {v:3, version, issued_at, salt_b64, set_id, stride}`: `version` is a strictly increasing integer (never reused, never lower, kept across restarts); `salt_b64` is 32 random bytes, new for every version; `set_id` is
  SHA-256 hex of the sorted (project, name, gen, retired) list; `stride` is the constant 9 in every file (the floor value of v2; a smaller stride only adds probes, and a copy of at least 32 characters of a form always contains a window at a multiple of 9), never derived from a key. There is no `baseline` member (the box has no repositories; devbox's matcher treats absence as empty).
- `entries`: an entry's identity is its index in `entries` (`entry` in a probe is that index). `form` is a form NAME from the closed list `raw`, `b64s0`, `b64s1`, `b64s2`, `b64u0`, `b64u1`, `b64u2` (standard and url interiors at byte alignments 0 to 2), never form text. Windowed: `{project, name, gen, retired, tier:"windowed", form}`, seven entries per generation, with no `len` and no digest. Anchored: `{project, name, gen, retired, tier:"anchored", form, anchor, len, digest}` where
  `anchor` is the form's leading characters fixed by prefix bytes alone (the adapter's public prefix in that form) and `digest = HMAC-SHA256(salt, the following len characters fixed by core bytes alone)` as hex, no windows; `len` is the one length the share file carries (`KBOX-2`). Forms come from
  `shareForms` (`KBOX-54`): raw and the six base64 interiors; hex, percent and `\u` forms are never shared.
- `probes`: every windowed entry has exactly **40** probes `{entry, j, d}`, with `j` = 0, 9, 18, … 351, whatever the key's length. `d` is `HMAC-SHA256(salt, form[j:j+24])` as hex for each real window (a window lies wholly inside a random core: none touches a prefix, a JWT header or payload) and 32 random bytes as hex for each remaining slot (a **decoy**, indistinguishable by any field). The largest windowed form (base64 of a 256-character core, 342 characters) has 36 windows, so 40 covers every eligible key. A hit is a window whose HMAC equals a probe's `d` (full 32-byte equality; a matcher may index the first 4 bytes for speed); the window holds at least 72 bits (`KBOX-18`), so a hit is a verified find, and the form starts at the hit position minus `j`. There is no BLAKE2b and no `len` for windowed entries, so the file is not a guess oracle (S-128) and does not reveal a windowed key's length.
- `coverage`: one item for every admin and master key `{project, name, gen, tier: windowed|anchored|none}`, so "not watched" is explicit.
Contents: current and retired generations of every admin and master key (ordinary keys are not in the file); a retired generation is watched while its value is still in the vault (the grace period), and once revoked its value file is deleted (`vault.retire`) so it leaves the file as `none`: a revoked key is dead, and keeping a dead admin value only to fingerprint it would add to what a box compromise yields (decided at build); the old Supabase database password and other keys that fail the shape check are `none`. The signing key is Ed25519, kept in the
vault as a master value, and its public half is in `GET /api/meta` (`box.share_public_key_ed25519_b64`) and in the control enrol answer. `GET /api/share` (scope `control`) returns the current envelope with the header
`KB-Share-Version: <version>`. A new version is written whenever a generation, a retirement or a coverage tier changes and is announced by one `share.version` event after the file is durable. **Wiring (owned by this unit):** the share writer runs at start and on every `key.changed` event (`KBOX-31`) for a key of class admin or master, so `rotate` and the retire route need no code from this unit, only the event (`KBOX-34`, `KBOX-51`). **The signing key:** at first start, with no share key in the vault, the writer generates the Ed25519 key, stores it as a master value and publishes its public half; a restart reuses it. Test (`test/share-file.test.ts`,
`test/fixtures/share-v3/`): the box-written file over a synthetic store of fake values is read by a **reference matcher written in the test kit from devbox admin-secrets-spec §4's CI backend** and finds every planted raw and
base64 copy (all six alignments, wrapped at 64 and 76 columns) and nothing else; a prefix-cut anchored copy is not found (documents the limit); two stores that differ only in key length (windowed cores of 32, 64 and 256 characters) give windowed entries and probes of the same count and the same `j` set, bodies of the same size, and no `len` member on any windowed entry (closed schema); `form` is always one of the seven names; a long human-chosen paste that fails the shape check has no entry and only a `none` coverage item; a `key.changed` emitted through the event port after a generation change, a retirement and a tier change each gives a new `version` and one `share.version`; first start generates the signing key once and a restart reuses it and `GET /api/meta` shows its public half; a 28-character `GOCSPX-` core gets an anchored entry and no windows; no window
covers a prefix or JWT header; `version` strictly increases across restarts and after a crash between write and announce (the file is never announced before it is durable, never rewritten with a lower version); the signature
fails on one flipped body byte; no core byte of any canary is in the file beyond the declared public prefix and `anchor` equals the adapter's public prefix; HMAC and Ed25519 known-answer vectors pass. The corpus
(`store.json` of synthetic values, `share.json`, `planted/*`) is the cross-repo golden that devbox unit 9 runs against its `admin-match` v3 backend; this closes the ordering gap noted in "Contradictions".

**`KBOX-55` The box's own Google signing key: made at start; rotated by publish, wait, prove, switch.** Source: `KBOX-41`; decided 2026-11-12.

**Creation.** Core makes the key at start when all of these hold: `KB_DOMAIN` and `KB_OIDC_AUDIENCE` are set, the rotation store is open, no other `google` master row exists, and `google/p/OIDC_SIGNING_KEY` has no `current` generation. Core draws 32 random bytes, drawing again until they are a valid P-256 scalar, and stores exactly those bytes as 43 base64url characters in the vault as generation G (the highest so far plus 1; 1 on a fresh store). Then, in this order, each step safe to repeat: the key row if absent (class `master`, status `works`, `gen_current` G, no destinations, `rotate_every_days` 90, `grace_hours` 1); `putKeyInfo(keyref, { scopeItems: [], location: {}, rotatedAt: now, markAdmin: false })`, without which `start()` throws `not_found`, `step()` fails with `no_adapter` and the key never falls due; then generation G as `current`. A crash after the vault write leaves no `current` generation, so the next start finishes the job; the orphan value was never published. A restart with a `current` generation does nothing. If another `google` master row exists, creation does nothing and audits `box_key.conflict`.

It needs no approval. Like the share key, it grants nothing until the owner, in their own Google project, makes a pool and provider that trust `https://keys.<domain>`. It is not a paste task, because no outside party issues it.

**What it never does.** The key is never made, replaced or given a generation through `POST /api/keys` or `POST /api/retired` (before or after creation); both answer `rejected` (`box_made`). Checked and closed: the only other writers of key rows or generations are the `add_key` executor (reached only from `POST /api/keys`; `add_key` is not a `POST /api/proposals` kind), paste completion (a paste task is opened only from `POST /api/keys`), a run started with a pasted value (never offered to a box key), and the share key's own vault write (a different ref). A proposal to grant it, add a destination to it, demote it or delete it is `rejected` (`box_made`). A `set_schedule` for it with `grace_hours` 0 is `rejected`.

**JWKS.** The JWKS lists the key's generations whose status is `pending`, `current` or `grace`, newest first, chosen by status and never by arithmetic on `gen_current`. A generation the vault cannot lend is left out. Assertions are signed only with `gen_current`.

**Due only once proven.** The proof mark is `rotation_gens.proved_at` (`KBOX-56` migration 2): null until an STS exchange signed with that generation succeeds, then the time of the first such success (`markProved(keyref, gen, at)` writes it only while it is null). It is set whether the exchange is a mint's (the minter reports each success to the store) or a rotation's proof (the new generation is marked before promote). `tickKey` skips a box key whose current generation has `proved_at` null: no approval, no notice. A `POST /api/rotations` by the owner still opens one. A run that fails `jwks_not_taken` sets `proved_at` back to null on the generation that stays current (`clearProved(keyref, gen)`), so an owner whose provider no longer trusts the box is not asked to approve a rotation each day.

**Rotation.** The `rotate_key` approval: never a paste task, due under `KBOX-52` like any master once proven. The steps (`stepsFor` leaves out pushing and redeploying, which would call `masterOf`):
- `issuing`: draw a new value, store it as generation N' (the highest so far plus 1) and mark it `pending`. The JWKS now lists it.
- `verifying`: check that it opens as a P-256 key. On leaving this step, set the run's wait time (`revoke_at`) to now + `JWKS_PUBLISH_LEAD_MS`.
- `checking`: wait until the wait time. Then prove: sign an assertion with N' and exchange it at STS. A refusal or no answer is retried with the `KBOX-17` backoff until `opened_at` + 2 × the lead; after that the run fails with `jwks_not_taken` or `sts_unreachable`. With no audience configured the run fails with `identity_unconfigured`.
- `promoting`: the run fails with `pending_missing` unless the vault lends N'. Otherwise N' becomes current, N goes to grace, and the wait time becomes now + grace.
- `grace`: wait.
- `revoking`: retire N and delete its value, so it leaves the JWKS. This is the one exception to `KBOX-51` step 10 (confirm the old key dead): the box is the only holder of the private half and no verifier exists to ask, so deleting the value is the death.

The run has no push and no redeploy. A failure rolls back as in `KBOX-17`, except that the box path never calls `masterOf` (not in rollback, revoking or any step; a second `google` master would give `master_ambiguous`): N' is marked `failed` and its value deleted, so it leaves the JWKS at once; N stays current; the owner gets one notice.

**The lead.** `JWKS_PUBLISH_LEAD_MS` is 24 hours, UNVERIFIED (probe `google.jwks-cache-duration`; Google documents no cache time). One day is longer than common JWKS cache times and costs nothing: the old key works throughout. The STS proof means a lead that is too short gives a later switch or a failed run, never a broken identity. The owner's provider must fetch keys from the issuer URL: with an uploaded JWKS, Google never sees N' and every rotation fails with `jwks_not_taken`. The wait time is kept in the run row, so a restart re-arms the timer.

## Decided while writing

1. **Toolchain** (Node 24 LTS, type stripping, `tsc --noEmit` dev-only with `@types/node` as the second and last dev dependency, `node:test`, strict flags): the choices the brief asked for; the table above.
2. **Two extra units** (`scaffold`, `forms`) and two splits (kernel into store and approve; unit 8 into five) so each seat sees one concern.
3. **Rule ids 27 to 54** are written for this spec; each cites the design section it makes buildable. Ids 1 to 26 are the design's.
4. **No `SO_PEERCRED`**: Node has no peer-credential API, so socket mode and directory ownership are the access check (`KBOX-3`, `KBOX-45`).
5. **Wire frame** (`KBOX-29`): error shape, code list, 64 KiB JSON body bound, `*_at` integer milliseconds, request ids, `KB-Api-Version`.
6. **Event and meta shapes** (`KBOX-30`, `KBOX-31`): the closed event-kind table, integer cursor, 25 s hold, an empty batch at timeout, events never deleted.
7. **Action kinds and enrol routes** (`KBOX-53`): the closed list of fifteen kinds; unauthenticated `POST /api/enrol` and its status poll; `control` enrol needs the window, `relay` enrol only proposes.
8. **Approver-add registration**: a one-time 10-minute code shown on the approving app and typed at the registration step (the design lists the approval, not how the new device joins).
9. **Paste is the approval** for a paste-source add or rotate (one action per approval holds).
10. **Challenge construction details**: JCS restricted to integers; view challenge `SHA-256("kbox-v1-view" ‖ nonce)`; paste challenge `SHA-256("kbox-v1-paste" ‖ pasteId ‖ actionDigest ‖ nonce)`; operation challenge `SHA-256("kbox-v1-op" ‖ SHA-256(canonical operation JSON) ‖ nonce)`; the device-key signature is raw r‖s over the 32 challenge bytes.
11. **Words for codes**: 12 words from the BIP-39 English list (132 bits) for the setup, recovery and registration codes; only the hash is kept.
12. **Release hash text format** and mode normalisation (`0755`/`0644`); one pax global header first is accepted for `git archive`; health check is `GET /healthz` showing H within 60 s.
13. **Idle watch** reads `/proc` (no Oracle API call), keeps memory at 30% of `MemTotal` (design: above 25%), warns within 5 points.
14. **Relay**: pass headers per profile (several declared headers must agree), `GET /r/_/grants`, the `envForClients` maps (Google's is `KBOX_GOOGLE_RELAY_URL`), upstream connect timeout 10 s and no total timeout, failure codes `bad_token`, `bad_path`, `bad_query`, `method_override`, `upstream_unreachable`, `upstream_timeout`, `withheld`.
15. **Share file layout**: a signed envelope over the raw body bytes (no canonicalisation), no `baseline` member, form names not text, constant stride 9 and 40 probes per windowed entry (decoys pad), no BLAKE2b, `GET /api/share`, the `share.version` event only after the file is durable.
16. **Retired hand-off** (`POST /api/retired`) needs no phone approval (a retired value is never lent); a value failing the shape check is stored `none`.
17. **Deliveries**: list, `/value` octet-stream, ack; an unacked delivery older than the key's grace raises one notice and never stalls the run; ordinary class only.
18. **Rotation failure retry**: first retry at 1 minute, doubling to 1 hour (S-249 gives no numbers).
19. **Vercel operation routes** (`KBOX-26`): `POST /api/vercel/{projects,domains,settings}`.
20. **Forms oracle**: devbox's `admin-match` forms through its test seam if usable, else hand vectors plus the substring property; the builder reports which.
21. **The phone app** is plain `.js` with JSDoc under `checkJs` (no build step), so the approved bytes are the served bytes.
22. **Share reference matcher** in the test kit plus a golden corpus replaces unit 6's test against a devbox backend that does not exist yet.
